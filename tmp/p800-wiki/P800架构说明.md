## 1 概述

**昆仑芯 P800** 是昆仑芯 P 系列的数据中心 AI 加速产品，采用 XPU 异构架构：芯片内以 12 个 **XPU Cluster** 承担通用标量/向量计算，以 **XPU SDNN** 承担卷积、矩阵乘等张量计算，二者共享系统级 **Last Level Cache（LLC）** 与 96 GB **Global Memory（GM）**；对外通过 PCIe 5.0 连接主机、通过 **XPU Link** 实现芯片间互联 [R8][R10]。整机侧典型形态为 8 卡 OAM 服务器 HCCPK1（8 × P800 + 8 × CX7）[R1]，软件侧由 XRE 驱动/运行时、XTDK 编译工具链、XDNN/XCCL 等加速库与 XPyTorch 框架适配层构成 [R11]。

从资料描述可以归纳出三条设计主线：

1. **计算异构**：SDNN 面向卷积/矩阵乘等高密度张量运算，Cluster 面向标量、向量及不规则计算；两者通过统一的 GM/LLC 交换数据 [R8]。
2. **存储分层**：GM（96 GB）→ LLC（96 MB）→ SM（256 KB/Cluster）→ GSM/LM（32 KB/Group）→ 寄存器，容量逐级减小、带宽逐级提高；文档给出的访存优先级为 **LM > SM > GM** [R10]。
3. **调度下沉**：硬件任务调度引擎 SSE 按 Cluster 粒度分发 Kernel，软件以 `cluster_num` / `core_num` / `stream` 三个参数控制并行度 [R10]。

## 2 芯片架构

### 2.1 总体组成

XTDK 手册对芯片组成的描述是：**多个 XPU-Cluster、XPU-SDNN、系统级 Last Level Cache 和 Global Memory 内存控制器** [R8]。按层次可表示为：

```
P800
├─ 12 × XPU Cluster        通用标量/向量计算，每 Cluster 64 Core、256 KB SM
├─ XPU SDNN                张量引擎：L1_A/L1_B、矩阵转移单元、MAC、协处理单元
├─ 系统级 LLC              96 MB，可视为“更快更小的高速 Global Memory”
├─ GM 控制器 + HBM         96 GB，全芯片共享
├─ PCIe 5.0                主机接口
└─ XPU Link                芯片间互联
```

| 模块 | 职责 | 关键参数 |
| :--- | :--- | :--- |
| XPU Cluster × 12 | 通用标量/向量计算，Kernel 的实际执行载体 | 64 Core/Cluster；16 Group；4 Core/Group；SM 256 KB；LM 32 KB/Group [R8] |
| XPU SDNN | 卷积、矩阵乘等张量运算加速 | L1 缓冲 + 矩阵转移/运算/协处理单元 [R8] |
| LLC | 片上末级缓存，缓解 GM 访问压力 | 96 MB；可按 `XPU_MEM_L3` 分配 [R8][R10] |
| GM 控制器 + HBM | 主存，保存模型权重与张量 | 96 GB [R8] |
| PCIe 5.0 | 主机—设备管理、数据传输 | — [R8] |
| XPU Link | 芯片间高速互联 | 拓扑中以 `XL` 标识 [R5] |

### 2.2 计算单元

#### 2.2.1 XPU Cluster（通用计算）

每个 Cluster 由 64 个 Core 组成，内部再划分为 16 个 Group，每个 Group 含 4 个 Core [R8]。Cluster 内的组织结构如下：

```
XPU Cluster（64 Core）
├─ 16 × Group
│  ├─ 4 × Core
│  │  ├─ 32 × 标量寄存器 R
│  │  ├─ 12 × 向量寄存器 VR（512 bit）
│  │  └─ 4 × Mask 寄存器 MR
│  ├─ Local Memory 32 KB（Group 内 4 Core 空分复用）
│  └─ Group Shared Memory（从上述 32 KB 中划分）
├─ Shared Memory 256 KB（Cluster 内 64 Core 共享）
└─ 每 4 个 Group 共享 1 个 SFU（exp / log / sin 等）
```

要点：

- **Group 划分不是连续的**：Core ID 对 16 取模同余的 Core 属于同一 Group，即 `group_id = core_id mod 16` [R8]。
- **4 个 Core 时分复用 SIMD 算力**：同一时刻只执行其中一个 Core 的指令，即 4 个 Core 竞争同一套 SIMD 资源 [R10]。
- **SIMD 宽度 512 bit**：一条指令可处理 16 个 FP32/INT32/UINT32，或 32 个 FP16 [R10]。
- **寄存器独立**：每个 Core 独享 32 个标量寄存器、12 个向量寄存器、4 个 Mask 寄存器 [R10]。
- **SFU**：每 4 个 Group 配置 1 个 SFU，支持 exp、log、sin 等特殊函数 [R10]。
- **同步原语**：`sync_local()`（Group 内）、`sync_cluster()`（Cluster 内）、`sync_group_mask(mask)`（按 Group 组合同步）[R10]，函数签名与用法见 [R7]。
- **跨 Cluster 通信**：通过 Global Memory 上的 GM-AMO 原子操作完成 [R10]。

#### 2.2.2 XPU SDNN（张量计算）

SDNN（Software-Defined Neural Network）是昆仑芯自研的核心张量计算单元，专门加速卷积和矩阵乘 [R8]。其数据通路为 [R8]：

1. SDNN 接收外部数据或命令，**DMA** 把输入从 Global Memory / LLC 搬到 **L1 Buffer**；
2. **矩阵转移单元**把源数据搬入内核中的 **L1_A / L1_B** buffer，分别存放矩阵 A、B；
3. **矩阵运算单元**执行矩阵乘并累加，结果写回 L1 Buffer；
4. **协处理单元**完成前后处理，包括数据搬运、合并以及 Element Wise 激活等向量/标量计算。

从可观测性角度看，SDNN 内部同样按 **SDNN-cluster** 粒度被调度：XProfiler 可统计某算子请求的 SDNN cluster 个数、MAC/DS 子单元耗时与利用率 [R6]。例如资料中的样例算子 `quant_basic` 需要 6 个 SDNN-cluster 资源 [R6]。

#### 2.2.3 SSE 硬件调度

XPU 架构集成了硬件任务调度引擎 **SSE（Stream Scheduling Engine）**，按配置把上层任务动态分配给各 Cluster [R10]：

1. **Host 配置**：向 SSE 传入 Kernel 函数、Cluster 数量及参数；
2. **调度启动**：SSE 根据设备空闲情况依次启动 Cluster，配置 `cluster_num`、`cluster_id`、参数指针；
3. **Kernel 执行**：Cluster 内 Core 执行编译器插入的入口代码，读取参数、进入用户代码；
4. **完成反馈**：Kernel 结束后向 SSE 返回结果，SSE 等所有 Cluster 完成后下发下一个任务 [R10]。

调度特性对性能有直接影响：**同一 channel 内的任务串行下发**，且必须等待当前任务关联的所有 Cluster 计算完成，才能下发后续任务 [R6]。因此“算子占用 Cluster 数”与“Cluster 间负载是否均衡”会直接决定硬件空闲率。

### 2.3 存储层次

| 层级 | 容量 | 共享范围 | 软件视角 |
| :--- | :--- | :--- | :--- |
| Global Memory（GM） | 96 GB | 全芯片（所有 Cluster 与 SDNN） | 默认地址空间；`xpu_malloc` 分配；DMA 访问 [R8] |
| Last Level Cache（LLC） | 96 MB | 全芯片 | 可为 Host/Device 高速交互分配（`XPU_MEM_L3`）[R10] |
| Shared Memory（SM） | 256 KB / Cluster | Cluster 内 64 Core | Cluster 内共享数据与同步 [R8] |
| Group Shared Memory（GSM） | 32 KB / Group | Group 内 4 Core | 从 LM 物理空间中划分，按 Core 平摊配额 [R10] |
| Local Memory（LM） | 32 KB / Group | Group 内 4 Core（空分复用） | 默认地址空间；编译器自动分配 [R10] |
| 寄存器 | 32 R + 12 VR + 4 MR / Core | 单 Core | 编译器分配；SIMD 运算的操作数来源 [R10] |

数据搬运规则 [R10]：

- 片内提供专用 **DMA** 硬件，在 LM、SM、LLC、GM 之间搬运数据，不占用寄存器；
- 提供 `GM2LM`、`GM2SM`、`GM2GSM`、`SM2GM`、`LM2GM`、`GSM2GM` 等接口；
- **不支持 GM 直达寄存器**；SIMD 计算需先把数据从 LM/SM 拷入向量寄存器，算完再回拷；
- 主机与设备之间通过 PCIe 传输，文档建议尽量减少跨端传输，并把小数据打包传输 [R10]。

设计含义：GM 容量大但延迟高，LLC 是“更快更小的高速 GM”，SM/GSM/LM 才是 Kernel 内真正的低延迟暂存。文档明确给出的优化顺序是 **Local Memory > Shared Memory > Global Memory** [R10]。

### 2.4 互联

- **主机接口**：PCIe 5.0，承担 XPU 与主机之间的管理及数据传输 [R8]。
- **芯片间互联**：XPU Link；`xpu-smi topo` 中以 `XL` 表示“经由 XPU Link 的连接” [R5]。
- **PCIe 产品的卡间互联模式**：默认 4 卡全互联，可通过 `/etc/modprobe.d/kunlun.conf` 中 `KLreg_RegistryDwords="PcieLink=n"` 切换：`0`=4 卡、`1`=8 卡、`2`=16 卡、`3`=16 卡 TP8 互联；OAM 产品无需配置 [R5]。
- **拓扑标识**：`xpu-smi topo` 用 `X`（自身）、`XL`（XPU Link）、`PIX/PXB/PHB/NODE/SYS`（不同层级的 PCIe/NUMA 连接）描述设备间关系 [R5]。
- **机柜级**：文档提到 32 卡机柜场景下 `xpuLinkInfo` 包含 `serverid`、`xpuid` 等信息 [R5]。

## 3 整机与集群

### 3.1 整机形态

| 机型 | 定位 | 配置 | 说明 |
| :--- | :--- | :--- | :--- |
| HCCPK1 | 正式机型 | 8 × P800 + 8 × CX7 | 裸金属产品 [R1] |
| HCCPK1t | POC 机型 | 8 × P800 + 8 × CX7 | 虚拟机产品 [R1] |

测试指导文档给出的软件基线：操作系统 TencentOS Server 3.1（TK4），内核 5.4.119-19.0009.56，OFED 驱动 5.8-2.0.3 [R1]。若系统盘较小，文档建议挂载本地 NVMe 到 `/data1` 并把 Docker 数据目录迁移过去 [R1]。

### 3.2 单机拓扑

单机 8 张 OAM 卡之间由 XPU Link 与 PCIe/NUMA 路径共同连接；`xpu-smi topo -m` 会列出 OAM0–OAM7 与网卡（示例中列出 NIC0–NIC5，即 mlx5_0…mlx5_5）的相对位置 [R5][R1]。示例拓扑中：

- OAM 之间既有 `XL`（XPU Link）连接，也有 `SYS`（跨 NUMA）连接；
- OAM 与网卡之间为 `PIX`/`NODE` 等级别的 PCIe 连接 [R5]。

这决定了多卡通信时的“就近”关系：同一 XPU Link 域内带宽最高，跨 NUMA/PCIe 主机桥则需经过更长路径。

### 3.3 多机扩展

- 每台整机配 **8 张 CX7 网卡**，测试文档以 `mlx5_bond_0` 为例做两机 RDMA 带宽/时延测试（`ib_write_bw`）[R1]；
- 多机通信需安装 **XDR 驱动**（可选组件，版本 1.1.0.4 / 1.1.0.10）[R1]；
- 部署规模上，文档覆盖 **单机 8 卡**与**双机 16 卡**；4 机以上建议做 topo 排序，否则跨机通信性能不是最优 [R1]。

## 4 软件栈

### 4.1 分层总览

```
模型/框架    XPyTorch（PyTorch 2.5.1）、Megatron、DeepSpeed、vLLM
专业库       XDNN · XFA · XFT · XBLAS · XFFT · XTLASS · XECV · XCCL
工具链       XTDK（LLVM）· XTRANSCUDA · XTRITON · XProfiler
运行时       XRE（kunlun 驱动 / libxpurt / xpu-smi / XPUML）
硬件         P800 OAM / P800 PCIe
```

开发栈被明确划分为三层：顶层专业领域高性能库、中层工具包（编译器与算子生成器）、底层驱动/运行时/硬件管理 [R11]。上表补充框架/模型层后形成五层视图（模型/框架、专业库、工具链、运行时、硬件），与 XPyTorch 手册的“软件栈层次”表一致（模型 / 框架 / 专业库 / 开发工具包 / 运行时）[R3]。

### 4.2 运行时 XRE

XRE 是昆仑芯 SDK 的运行时底座，包含 [R5]：

- **设备驱动**（`kunlun_module/kernel-open/kunlun*.ko`）与 udev 规则（`99-kunlun.rules`）；
- **运行时头文件**（`include/xpu/runtime.h` 等）与**运行时库**（`libxpurt.so` 等）；
- **运行时实用程序**（`xpu-smi` 等）与**运维工具**（`test_dma`、`test_launch` 等）。

驱动装载后通过设备文件（如 `/dev/xpu0`）暴露设备；XRE 支持的产品包括 P800 OAM、P800 PCIe、P600 OAM、P600 PCIe（Vendor ID `1d22` / `2057`）[R5]。xpu-smi 可查看 Driver Version、Runtime Version、显存/L3 使用、ECC、温度、功耗、时钟与进程 [R5]。

### 4.5 框架适配

**XPyTorch** 是面向昆仑芯的 PyTorch 适配方案：资料中的发布件为 `xpytorch-cp310-torch251-*`（Python 3.10 + PyTorch 2.5.1），以 Docker 镜像方式交付，兼容 Megatron、DeepSpeed 等并行框架，并提供模型仓与迁移样例 [R3]。推理侧测试文档大量使用 **vLLM** 部署，配合 W4A8/W8A8 量化与 `XINFER_QUANT_SDNN` 等开关强制走 SDNN 算子 [R1]。

### 4.6 运维与调优

- **xpu-smi**：设备列表、`topo -m/-mo` 拓扑、ECC、功耗、时钟、进程级占用 [R5]；
- **XProfiler**：支持 fork/attach 等模式，输出 timeline 与 flow 事件，可下钻到 SDNN 子部件（MAC、DS）与 Cluster 利用率，用于定位“硬件队列是否饱和、launch 开销是否过大、算子负载是否均衡” [R6]；
- **运维工具**：`test_dma`、`test_launch` 等用于功能与链路自检 [R5]。

### 4.7 容器与云原生

数据中心套件由 **XPU 容器工具包**与 **XPU Kubernetes 组件包**组成，支持在云上部署 XPU、使用虚拟化与多用户共享等能力 [R11]。测试文档中的容器启动方式为 `docker run --privileged --net=host --shm-size 256g` [R1]。

## 5 编程模型

### 5.1 异构执行

XPU 采用 Host（CPU）+ Device（XPU）的异构模型：Host 负责设备获取、数据准备、任务描述、Kernel 启动与结果获取；Device 侧用扩展的 XPU C/C++ 编写 Kernel，源文件以 `.xpu` 为后缀，Host 与 Device 代码可混合在同一文件中 [R8][R10]。

典型流程 [R8]：

1. 包含 `xpu/runtime.h`（由 XRE 提供）；
2. `xpu_set_device(0)` 选择设备；
3. `xpu_malloc` 申请设备内存，`xpu_memcpy` 在 Host/Device 间拷贝；
4. 创建 stream/queue，启动 Kernel；
5. 同步并回拷结果。

### 5.2 Kernel 启动

启动语法为 [R10]：

```
kernel_func<<<cluster_num, core_num, stream>>>(param1, param2, ...);
```

- `cluster_num`：逻辑 Cluster 数，取值 1–255；小于物理 Cluster 数时按需启用，超过物理数量时“打满后分批循环调度”；
- `core_num`：每个 Cluster 内的逻辑核数，建议设为每 Cluster 的逻辑核数；
- `stream`：多队列调度，多个 Kernel 的 `cluster_num` 总和不应超过物理 Cluster 总数（多 Queue 在 Cluster 级别并行）[R10]。

### 5.3 存储与数据搬运

- 地址空间修饰符显式声明：`__global__`、`__shared__`、`__local__` 等；函数参数中的指针默认位于 GM [R10]；
- LM 由编译器自动分配，GSM 从 LM 配额中划分，申请过多会导致 LM 不足 [R10]；
- SIMD 运算前需把数据从 LM/SM 拷入向量寄存器，计算完回拷 [R10]；
- 片内搬运优先用 DMA 接口（GM2LM 等），避免占用寄存器与额外指令 [R10]。

### 5.4 同步

| 指令 | 作用范围 |
| :--- | :--- |
| `sync_local()` | 同一 Group 内的 Core |
| `sync_cluster()` | 整个 Cluster 内的 Core |
| `sync_group_mask(mask)` | 按 mask 指定的 Group 组合 |
| GM-AMO 原子操作 | 跨 Cluster 的数据交换与累加 [R10] |

## 6 性能特征与调优

P800 的性能模型可以概括为“**向量吞吐 × SIMD 填充率**”与“**张量吞吐 × MAC 利用率**”两条主线，再叠加存储层次与调度开销。

| 现象 | 机理 | 调优手段 |
| :--- | :--- | :--- |
| 向量算子慢 | 4 个 Core 分时共享一套 SIMD，单 Core 难以隐藏延迟 | 让 Group 内 4 个 Core 都有均衡工作；向量化到 512 bit（16×FP32 / 32×FP16）[R10] |
| 访存瓶颈 | GM 延迟高、带宽有限 | 数据尽量驻留 LM/SM；用 DMA 批量搬运；减少 GM 读写 [R10] |
| Host-Device 拷贝多 | PCIe 传输慢，小包效率低 | 中间结果留在设备侧；小数据打包传输 [R10] |
| Cluster 空闲 | SSE 按 channel 串行，等待所有 Cluster 完成 | 均衡算子占用的 Cluster 数；算子融合；拆分长尾算子 [R6] |
| launch 间隔大 | Host 下发密度不足 | 降低用户态开销、算子融合；用 XProfiler 观察 stream 间隙 [R6] |
| 多卡扩展差 | 跨 NUMA/PCIe 路径长 | 按 `xpu-smi topo` 摆放进程与网卡；利用 XPU Link 域内通信 [R5] |

XProfiler 手册给出的 resnet50 样例可以说明如何读这些指标：SDNN 与 Cluster 的执行耗时占比分别为 95.1% 与 4.6%，说明负载以张量计算为主；进一步下钻，MAC 单元利用率 61.3%、DS 单元 48.5%，即“硬件队列接近饱和，但 MAC 仍有提升空间” [R6]。同一手册还给出 `quant_basic` 算子占用 6 个 SDNN-cluster、呈线性完成、空闲等待明显的案例，用于说明负载不均衡的识别方法 [R6]。

## 8 资料边界与版本差异

### 8.1 资料未披露项

以下参数在 11 份文档中均未出现，本页不做填充：制程工艺、晶体管数量、Die 面积、峰值算力（TFLOPS/TOPS）、HBM 带宽、XPU Link 单链路带宽、NoC 拓扑细节、SDNN 每芯片数量、官方 TDP（仅有 xpu-smi 样例 400 W）、ECC 实现细节、LLC 关联度等。

### 8.2 需要注意的口径

- **96 GB 是 Global Memory 容量**，不是“卡上总缓存”；LLC 为 96 MB，两者相差三个数量级 [R8][R5]。
- **400 W / 1450 MHz 是 xpu-smi 样例读数**，不等于官方规格书功耗/频率 [R5]。
- **PcieLink 参数是 PCIe 产品的卡间互联模式**（4/8/16 卡），不是主机链路速率；OAM 产品跳过该配置 [R5]。
- **“768 Core”是 12 × 64 的推算值**，文档直接给出的是每 Cluster 64 Core、共 12 个 Cluster [R8]。

### 8.3 版本差异

- **XTDK**：V3.4（2025-07-29）与 V3.5（2026 年两个发布件）在编程模型章节结构上基本一致；V3.5 增补了 SIMD 指令、数据迁移等细节（本页主要引用 V3.5）[R8][R10]。
- **XRE**：V3.7（2026-04-30，54 页）较 v3.4（2025-07-17，47 页）增加了 xpu-smi、XPUML 与运维工具相关内容；本页以 V3.7 为准 [R4][R5]。
- **文档日期不一致**：两份 XTDK V3.5 的封面均写“文档时间 2025-11-13”，而文件名分别为 2026-04-15 与 2026-10-13；本页引用时以“V3.5（2026 发布件）”区分，不采信封面日期 [R9][R10]。

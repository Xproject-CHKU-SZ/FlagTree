对我们的影响
1Kernel / ISA 入口写 kernel、发指令
源码Triton + TLE-Lite/Struct/Raw + PTX inline asm
可写Triton + inline asm + tle.raw(xpu3) + tle.gpu
两家都开。厂商的手写内核口子是开的，所以 tle.raw 能绕路。
2Python 前端API 语义与实现
源码triton.experimental.tle 全量 .py；声明 38 个 TLE 原语
半封闭__init__.py 可见；semantic/spaces/types 是 .abi3.so；声明 0 个原语
改不了 API 语义；连 is_tle_supported 都不存在。
3方言定义.td / .h / op 类型
源码TritonGPU / TLE 的 TableGen 与头文件全量
封闭TritonSDNN/IR 只有 CMakeLists.txt，没有 .td/.h
加不了新 op；SDNN 的类型/属性对我们是黑盒。
4Pass / lowering把 op 降到硬件
源码TritonNVIDIAGPUToLLVM 全量 C++（该目录 21 个 .cpp）
封闭36 个 SDNN pass 只有 .o；该后端 47 个 .o 无源码
DSA 数学/local_ptr 没地方降；只能等厂商在 .o 里加。
5运行时 / 驱动工具链与设备
二进制CUDA driver / ptxas / SASS
二进制xpu3 工具链 / 驱动 / 预编译 .so
两家都一样，不是本次的差异点。
47个 .o 没有对应源码，全部落在 SDNN/DSA 这条链上
36个 TritonSDNN pass 只有 .o，0 个 .cpp
38 : 0TLE 原语声明数量（NVIDIA : XPU）
4个 DSA Python 模块是 .abi3.so，仓库只剩 __init__.py
结论：保守的不是指令集，而是方言 + 绑定 + lowering。这三层恰好是给 TLE 加 DSA 数学必须经过的地方——所以 tle.raw 能绕过去，正规 TLE 路径绕不过去。
但也要说公道：厂商并没有把门全关。kernel 入口、inline asm、tle.raw、tle.dsa.copy 的 DMA 通路都是开着的；封闭的是编译器中间层，不是硬件能力。

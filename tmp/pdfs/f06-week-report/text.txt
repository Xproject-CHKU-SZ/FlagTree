二、融合原理
融合在静态 FX 图上完成，而不是把任意相邻 Python 算子合并成单一 kernel。流程为：FX GraphModule 与输入元
数据 → 模板匹配 → 合法性、语义与后端守卫 → 固定执行计划 → 捕获外编译与预热 → 执行模板 kernel；若元数据
不满足或编译被拒绝，则回退原 FX 区域并记录原因。设备执行错误直接报错，不静默重试。
匹配要求相邻单消费者链、中间结果不外逃、无就地修改或未知副作用、主输入为静态连续二维张量、广播输入受模
板约束、同设备同 dtype，且处于推理模式。只有“融合且数值正确”的样本进入性能统计，失败和回退不计入加速比。
显式语义 cast 保留原低精度中间舍入，epsilon、dim、keepdim 和广播语义保持不变；GELU exact 的 erf 与 tanh
近似保持为不同模板。
MatMul+Bias+激活尽量把乘积累加保持在 tile/epilogue 内，减少中间张量的全局写回、重读和启动开销。NVIDIA 合
格路径为单个 Triton matmul+epilogue；P800 FP16 对齐路径使用 SDNN dot 与扁平 epilogue，BF16 使用 native
torch.mm 加一个 Triton epilogue，尾部路径采用有界原生 MM+epilogue。因此 P800 的融合模式可能包含多个
kernel 或原生算子，不能表述为三个算子始终单 kernel 完成。

Add+GELU/SiLU 在同一合格内核内完成读取、加法、激活与最终写回。Add+Softmax 和 Add+LayerNorm 将加法与
行归约及归一化组合；LayerNorm 的均值和有偏方差使用 FP32 计算。Mul+Sum 先保留低精度乘法应有的舍入，再
以 FP32 累加行归约，减少完整中间张量的显存读写。不同模板保留各自的数值语义，不以改变近似算法换取速度。
cross-call 仅内联显式提供的 FX 阶段：首阶段接收全部输入，后续阶段只接收前一阶段单一输出，整条链必须匹配一
个合格模板，不会把任意独立调用自动拼接。
捕获前选参策略
当前选参采用“有限候选配置枚举 → 正确性校验 → 实测择优 → 固定配置执行”。针对每个匹配的融合区域，按设备、
精度、输入形状和步长以及算子语义分别确定配置；优化对象是该区域的内核执行参数。
  1. 生成候选：从预设的有限配置集合取候选，并按后端能力和输入尺寸筛选。

  2. 校验正确性：逐个准备并执行候选，与原始 FX 子图结果比较；编译、执行或数值校验失败的候选不参与择
     优。
   3. 实测择优：复用 FlagTune 事件计时协议，预热后比较耗时中位数，选择通过校验的候选中测得最快的一项；
      计时失败的候选也被排除。
   4. 固定执行：将结果保存为 TuningPlan ，传给 graph_fusion.compile 后使用固定配置。选参由调用方显式
      发起，编译规划阶段不自动搜索；配置在 CUDA Graph 捕获前确定并预热，捕获内部不执行 autotune。

四、问题与限制
P800 原始包侧共有 23 个数值校验失败样本，按无效样本从加速比统计中排除；这些不是当前 F06 实现的失败。当前
实现在两个设备上的 117 个样本均已通过数值校验。P800 捕获前选参后仍有 4 个 BF16 用例未超过 PyTorch
eager，其中 BF16 MatMul+Bias+精确 GELU 的 64×1024 用例也慢于原始包；32×256 用例相对 eager 为 0.996 倍，
接近持平，负收益主要集中在 BF16 精确 GELU，并包含 Add+Softmax；寄存器压力、归约布局和激活函数成本可能
抵消访存与启动收益。BF16 exact GELU 的剩余差距尚未完全定位根因，本轮也未宣称已修复全部 LLVM 限制或移除
原生算子路径。
RTX 4090 对照的 17 项 Inductor 数值失败与 P800 原始包的 23 项失败分别记录。4090 的 4.440× 结果仅针对当前软
件栈、默认 Inductor 模式和共同有效的小规模算子链；其同口径 Inductor 相对 eager 为 0.317×，需要继续区分运行
时调用开销和设备计算效率。其他 Inductor 模式、更大形状及完整模型仍需独立验证。

生成代码显示，MatMul+Bias 被降低为一次 extern_kernels.addmm 调用，外层仍有形状检查、设备上下文和输出
分配。它与 eager 的 mm 加 add 走不同的库调用路径；需要进一步区分库函数选择和包装开销，不能仅凭算子数判
断速度。
Mul+Sum 已将乘法与归约合成一个 Triton 内核，并省去了完整中间张量；32×256 与 64×1024 路径均采用
XBLOCK=1 ，每个 program 处理一行， RBLOCK 分别为 256 和 1024。耗时随形状发生大幅变化，说明仅用固定
Python 包装成本不足以解释，需要重点检查归约布局、执行调度及编译优化效果。上述配置与慢点相关，但尚无设备
事件或 CPU profile 证明其中哪一项是主因。
上层生成代码记录 CUDA facade 设备属性，实际编译记录和缓存已确认 XPU driver、arch=3、warp_size=1 及
xpubin 产物。接口兼容打通不等于上层归约启发式已经针对 P800 优化；也不能因为代码中出现 cuda 就判断执行了
错误后端。
下一步先拆分主机调用与设备执行时间，再对 addmm 、归约配置和编译选项做单变量对照。本轮证据不足以把全部差
距归因于 Python、LLVM 或某个具体 pass，也不能把结果外推为所有模型上 Inductor 都慢于 eager。分析依据见
Inductor 慢点核查。

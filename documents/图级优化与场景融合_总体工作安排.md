# 图级优化与场景融合总体工作安排

## 1. 目的与结论

本文定义 FlagTree“图级优化与场景融合”任务的工作范围、分阶段安排、交付标准与边界条件。它以当前工作树 `dev/rzh`（基线提交 `5eda9956b`）的真实能力为依据。

当前 FlagTree 的编译输入是 Triton AST、TTIR、TTGIR 等 Kernel 级中间表示；仓内未发现 PyTorch FX、TorchDynamo、TorchInductor 或 ONNX 的模型图前端。因此本任务分为两条依赖明确的路线：

```text
路线 A：FlagTree 原生编译 IR 优化
  TTIR / TTGIR -> 规范化、CSE、Cast/Layout 清理、Kernel 内融合

路线 B：可选图桥接与场景融合
  冻结的 FX / Export 图 -> 白名单匹配 -> 融合候选 -> 目标 Kernel / 回退图
```

路线 A 可立即开始，是第一阶段的工作范围。路线 B 不能跳过图入口、语义约束、fallback 和后端能力描述，不能直接把当前已有 TTIR/TTGIR pass 宣称为完整 PyTorch 模型图优化。

## 2. 目标架构与职责边界

```text
PyTorch 模型 / vLLM
  -> TorchDynamo / TorchInductor（模型图捕获、分解、Kernel 边界）
  -> Triton Kernel
  -> FlagTree（TTIR/TTGIR/LLIR 优化与后端 Lowering）
  -> 目标芯片 Runtime
```

FlagTree 的核心职责是优化和编译已形成的 Triton Kernel。后续图桥接的职责仅限于识别白名单子图、验证融合合法性、生成融合候选和维持回退路径；它不替代 TorchDynamo、TorchInductor 或完整模型推理引擎。

## 5. 用户使用流程

### 5.1 第一阶段：原生 FlagTree 编译优化

该阶段不引入新模型 API。用户继续使用已有方式：

```python
compiled_model = torch.compile(model, backend="inductor")
output = compiled_model(inputs)
```

或运行既有 Triton Kernel。上游产生 Triton Kernel 后，FlagTree 在 TTIR/TTGIR pipeline 内执行已启用的规范化和清理 pass。

```text
用户模型 / Triton Kernel
  -> torch.compile / Triton JIT
  -> FlagTree 编译 pipeline
  -> 优化后的二进制
  -> 目标设备执行
```

开发和验证流程为：

```text
选择固定 Kernel/Shape/Dtype
  -> 导出未优化基线 IR 和结果
  -> 启用候选 pass 或规则
  -> 导出优化 IR
  -> FileCheck/结构统计
  -> 参考结果比对
  -> 设备 Kernel 微基准
  -> 记录结论或回退原因
```

### 5.2 后续：图桥接与场景融合

图桥接仅面向被冻结的推理图：

```text
FX GraphModule / ExportedProgram
  -> 图规范化
  -> 白名单模式匹配
  -> 合法性检查
  -> FusionCandidate
  -> 后端 lowering 或原图 fallback
```

`FusionCandidate` 至少应包含：规则 ID、命中节点、输入输出 Tensor 规格、dtype/Shape/Layout 约束、目标后端能力约束、回退图或回退标识。

## 6. 明确不做的事项

以下事项不属于本任务默认范围：

1. 重写或替代 TorchDynamo、AOTAutograd、TorchInductor；
2. 通用 PyTorch 模型图捕获、动态 Python 控制流编译和 Autograd；
3. HuggingFace 模型加载、权重转换、Tokenizer、模型服务、HTTP API、KV Cache 和请求调度；
4. 在无明确语义、Shape、排序规则时，按“搜广推”业务名称自动融合；
5. 为了减少节点而改变浮点舍入路径、量化语义、别名语义、原地写入语义或随机数行为；
6. 不具备目标硬件时声称跨芯片性能通过；
7. 将训练反向与训练吞吐纳入默认验收。训练只在另行明确 backward、梯度精度和 step-time 要求后进入独立工作包。

## 7. 验收体系

### 7.1 基线定义

| 名称 | 定义 |
|---|---|
| Baseline | 同一 FlagTree 提交、相同后端、关闭新增规则或使用规则变更前 pipeline |
| Optimized | 同一环境启用新增规则或新 lowering |
| Reference | 厂商 Native PyTorch 或未编译 PyTorch；用于端到端定位，不用于单个 pass 的唯一归因 |

`Baseline -> Optimized` 是编译优化是否有效的主对比。所有测量必须固定设备、驱动、FlagTree SHA、Torch/Triton 版本、dtype、Shape、batch、seq len、随机种子、warmup、迭代次数和同步方式。

### 7.2 通用完成门槛

每个规则或场景候选均须满足：

1. **合法性**：命中条件、禁止条件与 fallback 条件明确；
2. **结构证据**：保存优化前后 TTIR/TTGIR；对于图桥接还需保存图前后或候选描述；
3. **正确性**：无 NaN/Inf，输出 Shape/dtype/device 正确；第一阶段的语义保持变换优先要求逐元素一致，不能做到时必须说明舍入原因并给出算子级容差；
4. **回退**：负例或不满足约束的输入保持原行为；
5. **性能**：Kernel pass 至少无可复现性能回退；只有在固定热点 Shape 与稳定测量基线后才设置特定加速阈值；
6. **可复现**：提供命令、输入、环境版本、IR dump、结果和日志；
7. **测试**：至少包含一个正例、一个负例和一个端到端执行例。

### 7.3 分层性能指标

| 层级 | 必测指标 | 适用对象 |
|---|---|---|
| IR 结构 | 常量/重复表达式/Cast/`ConvertLayoutOp`/临时 Store 数量 | 规范化、CSE、Cast/Layout 清理 |
| Kernel 微基准 | 平均、P50、P95 延迟；必要时带宽或 TFLOPS | 原生 pass、融合 Kernel |
| 子图 | 子图时延、Kernel 数、中间 Tensor 落地次数 | MatMul/Bias/Activation、检索子图 |
| 场景端到端 | Query P50/P95、QPS、分段耗时 | 搜广推场景 |
| 编译质量 | 编译成功率、冷编译/热缓存耗时、资源失败数 | 所有阶段 |

当前阶段默认只测推理。训练性能不与推理编译优化混合验收。

## 8. 风险与前置依赖

| 风险/依赖 | 影响 | 处理原则 |
|---|---|---|
| 图前端缺失 | 场景融合无法直接落入 FlagTree | 先完成原生 IR 路线，再设计最小、可选图桥接 |
| 后端 pipeline 差异 | Pass 顺序改变可能引发性能或正确性回归 | 分后端比较和接入；禁止全局硬编码同一顺序 |
| 浮点 Cast 与量化 | 错误清理会改变数值语义 | 仅做可证明等价的 identity/dead Cast；非精确折叠必须单独建规则和容差 |
| Layout 成本模型 | 少一个 Convert 不一定更快 | 同时检查寄存器、共享/本地内存、同步和实测时延 |
| TopK 语义 | 不稳定排序与 tie-break 可能造成业务结果差异 | 冻结 K、排序方向、mask、tie-break、dtype、候选规模 |
| 硬件可用性 | 无设备不能验证性能 | 区分 IR/编译通过、设备正确性通过、性能通过三种状态 |

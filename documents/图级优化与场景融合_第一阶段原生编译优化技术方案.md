# 图级优化与场景融合第一阶段：FlagTree 原生编译优化技术方案

## 1. 范围与目标

第一阶段只在 FlagTree 已有的 Triton 编译 IR 内工作，目标是把现有规范化、公共子表达式消除、冗余 Cast 清理、Layout 清理和 Kernel 内模式合并形成可验证、可诊断、可逐步扩展的编译优化能力。

本阶段优化对象：

```text
Triton AST -> TTIR -> TTGIR -> LLIR
```

本阶段不接收完整 PyTorch `nn.Module`、FX Graph、ATen Graph 或 ONNX 图；不实现模型图捕获、通用跨 Kernel 融合、Autograd 或推理服务。

首要目标是建立真实基线和可靠验收链，而不是在未量化现有 pass 行为前新增大量重叠规则。

## 2. 当前实现基线

### 2.1 PPU pipeline

在 `third_party/ppu/backend/compiler.py` 中：

```text
TTIR:
  inliner
  tensor pointer / descriptor rewrite
  canonicalizer
  triton-combine
  reorder-broadcast
  CSE
  symbol DCE
  loop unroll

TTGIR:
  coalesce
  remove-layout-conversions
  optimize-thread-locality
  accelerate-matmul
  optimize-dot-operands
  loop-aware CSE
  fuse-nested-loops / LICM / select-if combine / schedule / pipeline
  prefetch
  AIU lowering
  reduce-data-duplication
  instruction reorder
  SCCP / CSE / canonicalizer
```

PPU 已具备较完整的 pass 链。第一阶段的主要工作是确定现有 pass 对目标模式的覆盖范围、补足实际缺口，并避免因重复 pass 或不当顺序引入回归。

### 2.2 已有可复用 pass

| 能力 | Pass / 实现 | 说明 |
|---|---|---|
| 规范化与常量折叠 | MLIR Canonicalizer、SCCP | 已由后端在不同阶段接入；需分别确认 TTIR/TTGIR 覆盖 |
| 通用 CSE | `passes.common.add_cse` | 仅对等价且无副作用的表达式生效 |
| 循环 CSE | `triton-loop-aware-cse` | 可消除循环体中的等价迭代参数与子计算 |
| Kernel 内组合 | `triton-combine` | 已含 Dot+Add、AddPtr、Select/Load、Broadcast/Mul/Reduce 等规则 |
| Layout 清理 | `tritongpu-remove-layout-conversions` | 布局传播、重物化与清理；实现复杂，需按具体缺口扩展 |
| 数据复制处理 | `tritongpu-reduce-data-duplication` | 将部分 distributed->dotOperand 转换分解为 shared 路径，以便复用 |
| 循环融合 | `tritongpu-fuse-nested-loops` | 用于支持后续 pipelining，不是跨 PyTorch 算子融合 |

## 3. 第一阶段不做什么

1. 不新增 PyTorch FX/ATen/ONNX 导入器；
2. 不把 `MatMul + Bias + Activation` 作为第一阶段完整图融合交付；当前 `triton-combine` 的 `Dot + Add` 是同一 Kernel 的局部 IR 模式；
3. 不处理搜广推的 Normalize/Similarity/TopK/ReRank 业务子图；
4. 不以减少 IR 节点为唯一目标；任何变换都必须检查性能、资源和精度；
5. 不折叠会改变浮点舍入、量化、符号、bitcast、原地写入、随机数、原子操作、屏障或内存可见性语义的表达式；
6. 不变更 PPU、NVIDIA、AMD 等所有后端的 pass 顺序，除非完成对应后端的独立回归；
7. 不修改驱动、Runtime、模型源码或系统环境。

## 4. 技术路线

### 4.1 工作包 A：基线审计与规范化 profile

目标：从“源码中存在 pass”推进到“每个目标样例确认 pass 是否实际命中、输出如何变化、是否有收益”。

实施：

1. 选定首批覆盖集：
   - 常量算术与恒真/恒假条件；
   - 重复纯算术子表达式；
   - 循环体重复表达式；
   - identity Cast 和连续 Cast；
   - 连续 `ttg.convert_layout` 与 Dot 前后布局转换；
   - `Dot + Add`、连续 `AddPtr`。
2. 对每个样例记录：输入 IR、目标后端、pass 顺序、优化后 IR、统计值、执行结果和耗时。
3. 以现有后端 pipeline 为基础定义一个逻辑 profile，而不是复制一份全局新 pipeline：

```text
TTIR Normalization Profile
  Canonicalizer
  -> Triton Combine
  -> CSE
  -> Symbol DCE
  -> Loop-aware CSE（仅适用时）

TTGIR Cleanup Profile
  RemoveLayoutConversions
  -> ReduceDataDuplication（仅匹配且有收益时）
  -> Canonicalizer / SCCP / CSE
```

4. profile 的实际接入点由后端维护；PPU 是首个执行后端。NVIDIA/AMD 仅复用语义和测试，不假设同一顺序正确。

输出：pass 覆盖清单、样例目录、IR dump、命中/未命中说明、基线报告。

### 4.2 工作包 B：常量折叠与公共子表达式消除

目标：补齐现有 Canonicalizer/SCCP/CSE 在目标 TTIR/TTGIR 模式中未覆盖、且可证明语义等价的最小缺口。

规则分类：

| 类别 | 可优先处理 | 必须排除或单独论证 |
|---|---|---|
| 常量折叠 | 纯整数/布尔常量运算、恒定分支、shape/stride 常量计算 | 浮点重排、溢出语义不明确、带异常/undef 的操作 |
| CSE | 同 block、相同 operands/attributes/type、无副作用的纯表达式 | Load、Store、Atomic、随机数、Barrier、可能别名写入、跨控制流路径 |
| 循环 CSE | 循环不变量、等价迭代参数、相同纯子表达式 | 依赖 induction variable、循环写入、跨迭代可变值 |
| DCE | 未使用且无副作用的值 | 有内存、同步、诊断、调试或控制副作用的 op |

实现原则：

- 优先让已有 Canonicalizer、SCCP、CSE 处理；
- 若新增规则，只覆盖一个明确 IR 模式并在 pass 内给出 legality 条件；
- 不以 Python 文本匹配 IR 代替 MLIR pattern/rewrite；
- 新规则须同时提供正例、负例和 IR 断言；
- 优先放在 `lib/Dialect/Triton/Transforms`，仅当规则依赖 GPU layout/Memory Space 时才放入 `lib/Dialect/TritonGPU/Transforms`。

### 4.3 工作包 C：冗余 Cast 清理

目标：删除不改变数值与类型语义的 Cast，降低无效指令和布局传播障碍。

首批合法模式：

```text
cast<T>(x) where type(x) == T
  -> x

cast<T0>(cast<T1>(x)) where T0 == type(x) and both conversion steps are exact
  -> x

dead cast result
  -> DCE
```

首批禁止模式：

```text
fp32 -> fp16/bf16 -> fp32
fp32/fp16 <-> fp8
integer sign change / truncation / extension with value-range uncertainty
bitcast
quantize / dequantize
cast across memory operations or observable control flow
```

对于浮点和量化路径，只有当源 dtype、目标 dtype、操作顺序、舍入模式和数值范围均被显式证明等价时，才能建立专门规则；不能作为通用 Cast 清理。

### 4.4 工作包 D：Layout 转换与数据复制清理

目标：减少无效 `ttg.convert_layout`、不必要的重物化和可避免的数据复制，同时保持后端布局和硬件资源约束。

处理顺序：

1. 用已有 `tritongpu-remove-layout-conversions` 建立命中基线；
2. 确认目标 `ConvertLayoutOp` 是 identity、相邻可消、可安全传播或可由重物化消除；
3. 同时采集布局转换数、寄存器压力、共享/本地内存、同步数量和 Kernel 时延；
4. 仅对现有 pass 不能处理、且收益可复现的具体模式新增 rewrite 或成本条件；
5. 若转换用于满足 Dot/MMA/Load/Store 的布局约束，则不得为了减少 op 数强行删除。

`tritongpu-reduce-data-duplication` 的名字不代表“总是减少物理数据搬运”。其当前策略会将部分 distributed 到 dotOperand 的转换分解为 shared-memory 中间路径，以让 CSE 复用共享张量。因此必须以实际寄存器、共享内存、同步和时延结果判断是否收益。

### 4.5 工作包 E：同 Kernel MatMul 后处理审计

目标：明确当前 `Dot + Add` 能力的实际边界，并为后续 `MatMul + Bias + Activation` 图级模板提供 Kernel 层证据。

当前已知模式：

```text
tt.dot(a, b, zero) + d
  -> tt.dot(a, b, d)
```

该变换只适用于同一个 Triton Kernel、Dot 结果单次使用、累加器为零及满足 dtype/精度限制的模式。它不自动识别任意 PyTorch `Linear + Bias + Activation`，也不自动生成 fused epilogue。

第一阶段仅完成：

- 现有 `Dot + Add` 的正/负例审计；
- PPU/NVIDIA/AMD 后端对该 TTIR 规则的编译回归；
- 判断激活是否已经位于同一 Kernel 内，以及现有 elementwise lowering 是否避免额外落地；
- 输出进入第二阶段图模板所需的 legality 条件。

## 5. 代码与测试落点

| 内容 | 优先位置 | 原因 |
|---|---|---|
| TTIR 纯表达式规则 | `lib/Dialect/Triton/Transforms` | 与后端无关、可跨设备复用 |
| TTGIR Layout/Memory Space 规则 | `lib/Dialect/TritonGPU/Transforms` | 依赖 `ConvertLayoutOp`、Encoding 或 Memory Space |
| PPU 专属约束 | `third_party/ppu/lib` 或 PPU `compiler.py` | 仅当依赖 PPU MMA、AIU、Local Memory 能力 |

| IR 回归 | `test/Triton/*.mlir`、`test/TritonGPU/*.mlir` | 复用 `triton-opt | FileCheck` 基础设施 |
| Python/设备正确性 | `python/test` 或后端测试目录 | 覆盖真实 Tensor 和目标设备 |
| 基线与报告 | `reports/` 或任务专用结果目录，不进入 pass 源码 | 避免将机器相关 IR dump 写入源代码目录 |

## 6. 验证方案与完成标准

### 6.1 每条规则的最低测试集

| 测试 | 要求 |
|---|---|
| 正例 IR | FileCheck 断言目标 op 被折叠、替换或删除 |
| 负例 IR | 不满足 legality 时保持原 IR |
| pass 组合 | 验证新增规则与 canonicalizer/CSE/DCE 的顺序稳定 |
| 编译 | 至少一个实际 Triton Kernel 完成 TTIR 到目标二进制编译 |
| 数值 | 同输入与基线输出一致；第一阶段不改算术顺序的规则优先要求逐元素完全一致 |
| 性能 | 固定 Shape/Dtype 的设备 Kernel 基准；无可复现回退 |

### 6.2 结构指标

按规则至少记录一个主指标：

```text
常量节点数
重复纯表达式数
循环迭代参数数
Cast 数
ConvertLayoutOp 数
临时 LocalAlloc / LocalLoad / LocalStore 数
中间 global store 数
```

结构减少是证据，不是单独通过条件。若 `ConvertLayoutOp` 数减少但寄存器压力、共享内存或同步增加并造成性能退化，该优化不得默认启用。

### 6.3 性能测量

测量分为冷编译、热缓存和执行三部分：

```text
冷编译：清理对应 Triton cache 后记录 compile time
热缓存：保留 cache 后重复启动记录时间
执行：固定输入、warmup 后多次同步测量 Kernel latency
```

报告应至少包含：平均值、P50、P95、样本数量、设备、驱动、FlagTree SHA、Torch/Triton 版本、dtype、Shape、num_warps、num_stages 与 cache 状态。

首批规则不设置脱离具体 Shape 的统一加速百分比。通过门槛为：结构目标达成、数值正确、无稳定性能回退。对已确认热点 Shape，在完成基线噪声评估后另行冻结加速阈值。

### 6.4 设备与后端状态

状态必须分开记录：

| 状态 | 含义 |
|---|---|
| `ir_passed` | MLIR/FileCheck 通过 |
| `compile_passed` | 对应后端生成二进制成功 |
| `device_correctness_passed` | 真实目标设备数值通过 |
| `performance_passed` | 真实目标设备性能通过 |
| `not_run` | 未具备设备或环境；不能视为通过 |

PPU 是第一阶段优先设备。若 NVIDIA/AMD 环境不可用，可进行 IR/编译回归，但性能结论必须标为 `not_run`。

## 7. 实施顺序

1. **建立基线**：选择并冻结六类最小样例，确认现有 pass 和测试工具可运行；
2. **审计现有规范化**：对 PPU pipeline 输出 TTIR/TTGIR dump，形成 pass 覆盖矩阵；
3. **补充测试缺口**：先增加正例/负例，确认预期变换确实是缺口；
4. **最小实现**：一次只增加一条规则或一个受限的 pass 接入；
5. **IR 回归**：运行目标 lit 测试及相邻 pass 测试；
6. **设备验证**：执行单 Kernel 正确性与时延测试；
7. **扩展对象**：仅将已通过规则扩展到第二批 Shape/dtype/模型产生的 Kernel；
8. **固化结果**：记录规则、约束、收益、失败样例和回退条件，为图桥接阶段提供输入。

## 8. 第一阶段完成定义

第一阶段完成不等于“所有图融合完成”。完成应满足：

1. 形成当前后端 pass 覆盖、输入层级和实际边界的基线报告；
2. 建立 TTIR/TTGIR 规范化、CSE、Cast/Layout 清理的可复现样例与测试结构；
3. 对至少一项已有能力的实际缺口完成最小、可关闭、可回退的改进；
4. 改进具有正例、负例、IR 回归、编译验证和 PPU 设备正确性记录；
5. 固化性能测量方法，并对目标样例给出 Baseline/Optimized 对比；
6. 明确 `MatMul + Bias + Activation` 与搜广推场景融合进入第二阶段所需的图入口、语义约束和后端接口。

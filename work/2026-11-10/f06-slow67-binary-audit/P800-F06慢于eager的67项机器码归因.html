为什么 57 项选回 eager

27 项没有取得有效设备计时的替代候选，包含数值不通过、降层编译失败和 replay 计时无效。24 项有通过的候选，但最快的候选设备计时仍未超过 eager。另 6 项有设备更快的候选，正式入口仍选回 eager，包括 3 项 Add + SiLU 和 3 项 BF16 Add + GELU。逐项记录列出了候选、错误和选路数据。

  • BF16 MatMul + Bias + ReLU，2048×2048。SDNN 候选的 4,194,304 个输出里有 4 个超过容差，最大绝对差 0.125。正式入口因而执行厂商核。
  • BF16 2048×2048 Add + Softmax、Add + LayerNorm 的 v19 候选记录了 ConvertTritonXPUToLLVM 编译失败。BF16 512×1024 无 affine 的 LayerNorm 则有通过的 cluster 候选，但设备时间为 1749.90 µs，eager 为 17.35 µs。
  • BF16 2048×2048 Add + GELU（exact）在 v23 的混合双核为 262.13 µs，纯 cluster 融合为 3414.66 µs，eager 为 259.12 µs。已通过正确性校验仍可因性能回退。
  • v25 对 FP32 2048×2048 Mul + Sum 的独立探针记录了正无穷乘积，厂商整批归约输出 NaN，cluster 候选输出 +Inf。FP32 512×1024 Add + SiLU 的 SDNN 候选对 +Inf 输出 NaN，eager 输出 +Inf。这些差异解释候选拒绝，实际走 eager 的输出与其一致。

2 项设备也慢的 FP32 归约

64×1024 Mul + Sum 和 keepdim 在 v25 的正式端到端分别是 0.895× 和 0.884×。eager 先启动 tensor_calc_k_nk，再启动 reduce_mt，均为 12 clusters × 64 cores。乘法在 0x3e0 出现 vmul.f.mz.rn，归约在 0x4ec 出现 vadd.f.mz.rn。两种 F06 输出均启动同一个 _dsa_region_kernel，1 cluster × 8 cores。64×512 的行列分块把 64 行交给一个 program，每次把 512 列搬入 UNI_SRAM，乘广播系数并累加，随后沿列归约。

原融合核的 0x334–0x350 包含 dma_cfg 和 dma_run；更快的 8×512 核和原核均包含 17 处 dma_cfg、4 处 dma_run、22 处 xwait。比较静态指令无法计出动态 stall 周期。固定列宽的下表直接检验了行分块和并行度的影响。

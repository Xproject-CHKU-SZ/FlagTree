P800 BF16 Add + GELU

个人镜像 zhaoweiming/f06-p800:bf16-gelu-20261109-v22，ID sha256:184dbe68e942。两种 GELU 模式分别检验 64×1024、512×1024、2048×2048，第二个操作数均为沿末维广播的一维 BF16 偏置。

从设备指令定位数值错误

2048×2048 tanh 的原生 Inductor 在旧镜像上重现了与 v21 相同的机器码 b3f0e650ed 和 2,934,819 个普通输入超差。eager 按顺序启动广播 Add 与 GELU。原生 Inductor 在一个 cluster 核内读取两个 BF16 输入、做 FP32 运算，并在 Add 和 GELU 输出舍入。

原生旧码 0x6f0 的 addli r18, r18, 64 把 LM 输入偏移每次增加 64 字节。对应 LLVM 是 getelementptr <32 x bfloat>，接着只 load <16 x bfloat>。循环从第 17 个元素开始跳读，后续可超出本地暂存切片。新码 2ebfb73031 在同一大尺寸上的输入偏移按 32 字节推进，0x228 是 addli r17, r17, 32。LLVM 索引先乘 16，再按 BF16 字寻址。读写都按切片实际占用的 BF16 字数推进，奇数寄存器尾部取最后一个已加载的向量。

旧的成对 BF16 写回以丢弃部分的最低位处理舍入中点。新版用保留部分的最低位做最近偶数舍入，并保留 NaN 分类。标量及单个向量尾部显式写高 16 位，避免 LLVM 把 FP32 加法缩成舍入不同的 BF16 加法。旧标量 tanhf 计算 (eˣ−e⁻ˣ)/(eˣ+e⁻ˣ)，在正无穷处产生 NaN。cluster 降层将有序的大幅值参数限在 ±16（该处 FP32 tanh 已舍入到 ±1），NaN 继续传给原函数。

对固定 128×1024 输入，XBLOCK=4096 的独立原生探针只执行 FP32 广播加法时超差为 0，再加入 Add 输出的 BF16 往返舍入后旧码精确比较错 98,202/131,072 个。最终版 6 种块大小 × 7 种计算/读写方式共 42 项通过各自的零误差或 GELU 容差检查。

为何单个 cluster 核仍慢

每个模式和尺寸都用相同输入、相同图计时分别回放厂商 Add、厂商 GELU、两步 eager 和完整的正式 cluster。拆分 cluster 计算的对照沿用同尺寸调好的 XBLOCK 与 warp 数，每个样本回放 8 次，共 13 组。独立步骤各需读写自己的张量，其时间不直接相加预测融合耗时。

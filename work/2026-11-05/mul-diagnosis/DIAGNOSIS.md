# Mul + Sum 全部形状偏慢：根因定位（2026-11-06）

## 一、先看基线：eager 为什么快

在 152 上把 eager 的 `mul` 与 `sum` 两个 kernel 拆开测（fp32/fp16，2048² 流量 16MB）：

| 形状 | dtype | mul | sum | eager 合计 |
|---|---|---:|---:|---:|
| 16×128 | f32 | 10.7 µs | 8.9 µs | 18.6 µs |
| 512×1024 | f32 | 10.1 | 8.8 | 18.2 |
| 2048×2048 | f32 | 22.5 | 12.8 | 34.9 |
| 2048×2048 | f16 | 14.6 | 9.2 | **23.2** |

两个关键事实：
1. **单 kernel 地板约 9–10 µs**（16×128 的 mul 也要 10.7 µs）——小尺寸全部是启动开销，不是计算；
2. **厂商的 sum 极快**：2048² f32 只 12.8 µs（1.25 TB/s），f16 只 9.2 µs（1.7 TB/s），
   比 Triton 的最快 copy（1.06 TB/s）还快，说明它走的是厂商优化的向量归约核。

## 二、我们的四条路径实测

| 路径 | 16×128 | 512×1024 | 2048×2048 |
|---|---:|---:|---:|
| dsa（f32，DMA 融合核） | 23.3 µs | 22.6 µs | 31.7 µs |
| `_p800_reduce`（flat 两趟） | 25.3 | 35.0 | 185.8 |
| plain（f16 用，非 DMA 2D tile） | — | — | 112.8 |
| 朴素 2D 融合核（R×C + 循环） | **16.2** | 编译失败 | 编译失败 |

## 三、根因（分三层）

### 1. fp32 小/中尺寸（0.94–0.98）：dsa 固定开销打不过"两个 9 µs kernel"

- dsa 核在 8KB（16×128）问题上仍要 **23.3 µs**：LM 缓冲分配 + DMA 建链 + `mfence` + 启动，
  固定成本 ~13 µs，摊不薄；
- eager 两个 kernel 各 9–10 µs、合计 18.6 µs，反而更便宜；
- 而朴素 2D 融合核只要 **16.2 µs**（16×128）/ **15.3 µs**（32×256），本可以 1.15× 取胜——
  但它在 64×1024 以上 tile 时被后端 `TritonXPUCoreTiling` 编译失败挡住，接不进运行时。

### 2. fp16 全部（0.19–1.00）：没有可用的高速通路

- dsa 的 DMA 缓冲只支持 f32；f16 必须走位模式（一个 int32 塞两个 f16）；
- 我把 dormant 的 `_packed_kernel` 修通（两个编译 bug：`tle.dsa.copy` 的 dtype 不匹配、
  `tl.load` 后直接做 `& 0xFFFF` 缺 bitcast），但实测 **3.0 ms**（2048²）——
  因为解包用的整数位运算（`&`、`>>`、bitcast）在该后端被**标量化**，
  和我们之前测过的 fast-exp 位技巧（1265 µs）是同一个后端缺陷；
- 因此 f16 只能退回 plain（非 DMA）2D tile 核，读带宽只有 **0.14 TB/s**（117 µs @2048²）。

### 3. fp32 大尺寸（1.09–1.10）：唯一优势场景

- dsa 融合省掉一整趟 16MB 读：31.7 µs vs eager 34.9 µs → 1.10×；
- 说明"融合"方向本身是对的，问题只在小尺寸固定开销和 f16 通路。

## 四、顺带修掉的实现缺陷（本轮提交）

1. `_resource_runtime.py`：dsa 的 dtype gate 只放行 `float32`，f16 永远不尝试 dsa。
   放开后 f16 小/中尺寸从 0.91 → **0.97–1.00**；
2. `_p800_dsa.match`：当 m 不被任何候选行整除（如 m=16）时，autotune 会耗尽所有 tile
   并在**运行期**抛 `no correct tile`，导致整个区域失败（而不是回退）。加了 guard 后
   16×128 从"报错→回退"变成正常走 native 路径；
3. `_packed_kernel`：`tle.dsa.copy` 的 dtype 不匹配 + 整数位运算缺 bitcast，已修（暂不启用）；
4. rowsum 独立归约区域（b=None）在 `_measure` 里把 None 传给 kernel → `IndexError`，
   导致所有"单独 sum"区域永远 no correct tile（未修，已记录）。

## 五、修复后的 fp16 Mul+Sum（本轮实测）

| 形状 | 修前 vs eager | 修后 vs eager |
|---|---:|---:|
| 16×128 | 0.92 | 0.81 |
| 32×256 | 0.92 | **1.01** |
| 64×1024 | 0.91 | 0.99 |
| 128×1024 | 0.93 | 0.97 |
| 512×1024 | 0.48 | **0.72** |
| 2048×2048 | 0.15 | **0.19** |

## 六、要继续提升需要的三件事

1. **f16 走 DMA**：不要用整数位运算解包（会被标量化）。可行方向：
   - 在 dsa buffer 上直接按 f16 分配（若 TLE 支持 f16 buffer 就能 DMA 直通），或
   - 用 `tle.dsa.copy` 搬 f16 → 在寄存器里 `to(tl.float32)`（cast 是向量化的，不涉及位运算）；
2. **小尺寸路由**：把朴素 2D 融合核（16.2 µs）接进 `_p800_reduce` 的小尺寸分支，
   并在 tile 超过 8KB 时避开 `TritonXPUCoreTiling` 的编译失败（后端 issue #5）；
3. **减少 dsa 固定开销**：LM 分配与 fence 复用（每个 kernel 只建一次链）。

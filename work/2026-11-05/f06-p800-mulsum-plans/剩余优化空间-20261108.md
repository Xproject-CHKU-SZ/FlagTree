# 对比 eager：还剩下的优化空间（2026-11-08）

依据：本日实测地板（空闲卡 4–6）、F06 复测表、以及编译器源码里已具备但未启用的机制。
口径：2048×2048 fp32，memory floor copy1 = 32.7 µs、copy2 = 38.5 µs，launch floor ≈17 µs。

## 1. 最大的结构性差距：访存与数学没有重叠

| 项 | 时间 | 说明 |
|---|---:|---|
| copy1（1 读 1 写） | 32.7 µs | 纯访存 |
| sigmoid 点算子 | 75.7 µs | 数学部分 ≈ 43.0 µs |
| 两者相加 | 75.5 µs | **我们的 SiLU 实测 76.7 ≈ 相加** → 串行执行 |
| eager add+silu | 72.8 µs | **小于相加** → eager 有 DMA/计算重叠 |

结论：**我们的 Triton 点算子目前是"load → compute → store"串行**，eager 的
C++ kernel 能把搬运和计算重叠。若实现重叠，理想值 ≈ max(32.7, 43) ≈ 43–55 µs，
则：

| 模板（2048² fp32） | 现在 | 重叠后（估） | 对 eager |
|---|---:|---:|---:|
| add_silu | 78.4（0.92×，回退） | ~55 | ~1.3× |
| add_gelu_tanh | 81.6（2.50×） | ~55 | ~3.7× |
| add_gelu_exact | 173（erf 主导） | ~150 | ~1.7× |
| softmax / LN | 105–291 / 72.8 | 视归约结构 | 有改善空间 |

**机制已经存在**：`third_party/xpu/backend/compiler.py:435-447`
`add_tritonxpu_tle_pipeline_pass(..., TRITONXPU_TLE_PIPELINE, ..., lm_bytes_limit)`
会把循环里的 GM→LM fill 旋转成 prefetch，但**默认关闭**，且 kernel 需要用
`tl.range(num_stages=2)` 显式开启。这就是下一步最值得做的实验：
TLE 点算子（silu/gelu_tanh）在 `TRITONXPU_TLE_PIPELINE=1` + `num_stages=2` 下的时间。

## 3. 已经验证走不通的方向（不要再花时间）

1. **sigmoid 恒等式替代 exp**：σ(x)/(1−σ(x)) 实测 235 µs vs exp 70.8（慢 3.3×）；
2. **多项式 exp**（range reduction + 2^k 位拼接）：2447 µs（慢 34×，破坏向量化）；
3. **部分行 2D tile 归约**：1M 元素 1.1 ms（strided 访问退化），必须整行或 TLE；
4. **fp32 LUT 激活**：SDNN LUT 窗口 ±8，fp32 精度不达标（SiLU 余量 2.4e-3）。

## 4. 优先建议

1. **先做实验 1（TLE 流水）**：写一个 TLE 版 silu/gelu_tanh 点算子，`tl.range(num_stages=2)` +
   `TRITONXPU_TLE_PIPELINE=1`，与 pointer 版对比；若重叠生效，GELU/SiLU/softmax/LN 全线受益；
2. **实验 2（matmul+gelu_tanh split）**：改动小、收益确定（1.80×→2.1×）；
3. 实验 4/5 属于 tile 调优，顺手做；
4. 向量 erf、epilogue 融合、向量 exp 属于官方能力，列入需求清单。

# F06 Mul+Sum 三精度加速比（含本轮修复与方法）

测试日期：2026-11-06（P800 单卡 7 号，串行，无污染）
方法沿用本周报告口径：同一形状/精度下交替测试，逐例取中位数；只统计"融合且数值正确"的样本；
基线与融合分开统计；表中每格为"默认配置 / 捕获前选参（本轮为 tle.dsa 整核替换）"，单位 ×，大于 1 表示更快。

本轮"选参"指：bf16 XBLOCK 守卫（≤1024）、SDNN 关闭 coordinate-descent、以及 Mul+Sum 区域的
`tle.dsa` 2D-DMA 整核替换（含 tile 自动搜索与缓存）。

## 说明

- **FP32 是本轮唯一显著收益的精度**：`tle.dsa` 整核替换把 Mul+Sum 从 156 µs 降到 88.6 µs
  （相对 Inductor 1.78×）；归约单独替换为 103.1 µs（1.53×）。两者都通过了普通有限值与 8 种特殊值组合。
- **FP16 的 dsa 路径正确但更慢**（1133/1941 µs）：归约/乘法走 int16 位宽中转，2 字节 DMA 比 f32 慢约
  48×；相对 Inductor 只有 0.08×。在低精度上用 dsa 不划算，聚合时保留 Inductor 路径。
- **BF16 的旧 SDNN 路线在 2048² 上无法通过数值校验**（本轮定位为 XBLOCK 与 grid 不一致导致的欠写），
  修复为把 XBLOCK 限制在 1024 后 `cluster` 路线恢复为 100% 正确（312.3 µs）；dsa 乘法路线可用但
  5108 µs，暂不进入加速比统计。
- 小形状（16×128/32×256/64×1024）上 cluster 融合与 Inductor 基本持平（FP32 1.07×、FP16 0.88×），
  本轮 dsa 替换在这些形状不触发（列宽不足以分摊 DMA 开销）。

## 结论

- FP32：采用 `tle.dsa` 整核替换，相对原生 Inductor 1.53–1.78×；相对原 SDNN 拆分管线约 21.9×。
- FP16：保持 Inductor 路径（dsa 正确但慢 12×，暂不采用）。
- BF16：先应用 XBLOCK≤1024 守卫保证正确，路线仍用 cluster；dsa 路径待位宽中转优化后再评估。

## 重要更正：bf16/f16 的“算错”是对拍基准的错，不是核的错（2026-11-06 08:00）

复测脚本里用的参考是 `(a.float()*b.float()).sum(-1)`——乘积保留在 f32。但 PyTorch 对 bf16/f16
的语义是**逐元素乘积先按输入 dtype 舍入，再用 f32 累加**（`(a*b).float().sum(-1)`）。
用正确的基准复测同一批路线：

| dtype | 相对“f32 乘积”基准 | 相对“dtype 正确”基准 |
|---|---:|---:|
| bf16 | 0.223 | **0.0038**（2,048 个里 1,965 个 < 3e-3） |
| f16 | 0.0207 | **0.00047**（2,048/2,048） |

所以此前“bf16 资源路径仍然算错（max_rel 0.22）”的结论作废——**bf16/f16 的资源路径数值是对的**，
错的是我对拍用的 oracle。只有逐元素乘法的 XBLOCK 欠写问题是真实缺陷，已在前面修复并单独记录。

## dsa 在 f16 上为什么慢（拆解实测，2026-11-06 08:20）

把 dsa 路径拆成“纯 DMA”和“拆包/转换算术”两段（2048²，同样 64×128 tile、8 次循环）：

| 组成 | 耗时 |
|---|---:|
| 纯 DMA（f32 字搬进 LM + 平凡累加） | **16.6 µs** |
| dsa 打包版（DMA + 拆两个 f16 + 转换 + 乘加） | 3150 µs |
| dsa int16 版（2 字节 DMA + 转换） | 1053 µs |
| 普通 tl.load 核（转换在 LM 边界融合） | 111.7 µs |

结论：**DMA 本身不慢（16.6 µs，与 f32 的 22 µs 同量级）**；慢的是寄存器内的
`int16/f32字 → f16 → f32` 拆包转换——后端只在 LM 边界融合 dtype 转换，寄存器级转换按标量展开，
4M 个元素就放大到毫秒级。这也解释了为什么“打包成 4 字节”没用：字节宽度不是瓶颈，转换才是。


## 低精度改走普通 tl.load 核后的路线实��（152 卡 2，2026-11-06 08:35）

`_p800_dsa` 已按 dtype 分流：f32 走 dsa（片上 DMA），f16/bf16 走普通 `tl.load` 核
（f16 用 `to(f16).to(f32)` 舍入；bf16 因后端 cast 被折叠，用 RNE 手工位运算）。
tile 自动搜索 + 缓存，形状不整除自动回落。

| dtype | 路线 | 归约核 | 整条路线 | 相对 Inductor |
|---|---|---:|---:|---:|
| f32 | cluster 乘 + dsa 归约 | 22.15 µs | **100.4 µs** | **1.57×** |
| f16 | cluster 乘 + plain 归约 | 40.86 µs | **117.7 µs** | **1.57×** |
| bf16 | cluster 乘 + plain 归约(RNE) | 131.64 µs | 553.2 µs | 0.35×（变差） |

要点：

- f16 的归约核只要 40.9 µs（比手写探针的 111.7 µs 还快，因为路线内的 tile/参数更优），整条 117.7 µs。
- bf16 的归约核 131.6 µs 也不算差，但**整条路线 553 µs**——瓶颈在 bf16 的 producer（原生 cluster
  乘法核，受 XBLOCK≤1024 守卫后变慢），不是我们的归约。
- 结论：f32 与 f16 都已落地并达到 1.57×；bf16 需要先解决 producer 侧，暂不启用。


## bf16 producer 侧结论（2026-11-06 08:45）

拆开看 bf16 的乘法 producer（2048×2048 广播乘，8MB 读 + 8MB 写）：

| 实现 | 耗时 | max_rel |
|---|---:|---:|
| 原生 cluster 区域 | 413.8 µs | 0.0 |
| 普通 tl.load 核 32×512 | 1396.8 µs | 7.8e-3 |
| 普通 tl.load 核 64×256 | 3281.7 µs | 7.8e-3 |
| f32 参照（同形状） | ~20–30 µs | — |

结论：bf16 的逐元素路径在本后端**本身就慢**（f32 模拟 + 两次转换 + 8MB 物化），换 producer
写法救不了；只能靠**融合**避免物化中间张量。所以：

- bf16 保持 Inductor 融合核（194.3 µs），不用我们的拆分路线（553 µs）。
- f32 / f16 用我们的路线（各 1.57×）。

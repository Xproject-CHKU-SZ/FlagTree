# FlagGems 参考检查报告（`~/Documents/FlagGems`，v5.3.4-dev）

环境：XPU 后端 `_kunlunxin`，在 P800（镜像 20261113）上以 `PYTHONPATH=src GEMS_VENDOR=kunlunxin TRITON_XPU_ARCH=3` 直接运行。

## 1. 可直接复用的参考

### 1.1 `_kunlunxin/ops/exp2.py` —— 与我们的 exp2 修复一致

```python
LN2 = 0.69314718056
return tl.exp(x.to(tl.float32) * LN2)
```

即厂商参考实现也用 `exp(x·ln2)` 实现 `exp2`，印证官方 `tl.exp2` 在 XPU 上是错的（我们的 A1 修复方向正确）。

### 1.2 `_kunlunxin/fused/matmul_bias_activation.py` —— MatMul+Bias+Act 的完整 recipe

- bias 先物化为连续 `(M,N)`（1D bias 广播 epilogue 慢 1.2–1.4×）；
- tile：M≤512→BM=128；N≤512→BN=128，否则 bf16=256、fp16/fp32=512；BK：fp16=256，bf16/fp32=128；
- warps：小形状 4；**fp32 wide-N 必须 16**（w=8 会 mis-compile 到 1254 ms）；其它 8；
- 激活：小形状 / large-bf16 融合进 epilogue；**large fp16/fp32 必须拆成单独的 flat pointwise**（fp32 accumulator 上接激活会 `uni_sram` 或 dominate 编译失败）；
- dims/strides 全部 `do_not_specialize`（上游 #6415）。

### 1.3 `_kunlunxin/utils/codegen_config_utils.py` —— pointwise 官方 codegen 配置

`CodeGenConfig(512, (65536,65536,65536), 32, prefer_1d_tile, buffer_size_limit=4096, unroll_num=8, isCloseVectorization, isCloseMemoryAsync=True, kunlunAutoGrid)`；
num_warps：tile<2048→4，<4096→8，否则 16；已知坏 tile：`_BAD_TILE_SIZE_1D=32768`（回退 16384）。

### 1.4 `_kunlunxin/ops/softmax.py` —— TLE 版 row-reduce（最关键的编码参考）

- `tle.gpu.alloc(..., scope=tle.gpu.lmem)` + `tle.gpu.copy(desc, lmem, [XBLOCK,YBLOCK], [row, col])`（描述符 DMA）；
- 归约状态是 `[XBLOCK]` 向量（running max / sum-exp），沿列以 YBLOCK 流式推进，**无跨核 barrier**；
- 主 tile **不加 mask**（注释：masked 1D/2D tile 会退化成 per-lane gather，慢几个数量级）；尾部靠 copy clamp + `-inf` 预填；
- 分 fused（一遍 reduce+一遍 normalize）与 reduce+pass 两段两种；
- 几何：`_TLE_XBLOCK=256`、`_TLE_LM_BYTES_PER_CORE=2048`、`_TLE_CLUSTERS=8`，按行宽选择 XBLOCK/YBLOCK。

## 2. 在 P800 上实测 FlagGems（`flag_gems.enable()` 后走 vendor 实现）

| op | 形状 | FlagGems | eager | 比值 |
|---|---|---:|---:|---:|
| softmax | 2048×1024 | 85.0 µs | 33.2 | 0.39× |
| softmax | 2048×2048 | 167.0 µs | 53.2 | 0.32× |
| softmax | 512×1024 | 37.3 µs | 12.6 | 0.34× |
| layernorm | 2048×1024 | 486.4 µs | 17.9 | 0.04× |
| layernorm | 2048×2048 | 495.2 µs | 28.9 | 0.06× |
| layernorm | 512×1024 | 124.8 µs | 15.2 | 0.12× |
| matmul_bias_activation | 512×64×1024 | **编译器崩溃**（LLVM `CallInst::init` 断言：Calling a function with bad signature） | — | — |

对照我们自己的实现：
- softmax：我们 2048² 409 µs（FlagGems 167 µs，eager 53 µs）→ FlagGems 编码更好，但**两者都慢于 eager**；
- layernorm：我们 2048² 215.8 µs（FlagGems 495 µs）→ **我们的更快**；
- matmul：FlagGems 的参考 kernel 在当前 LLVM/工具链上**直接崩编译器**，不能照抄，只能借鉴其 tile/warps 规则。

## 3. 关键结论

1. **"按建议写"的 vendor Triton 库也打不过 eager**：softmax 0.32–0.39×、layernorm 0.04–0.12×——这两类在 XPU 上应继续回退（我们现在的策略是对的）；
2. **FlagGems 的 softmax 比我们的快 2.4×**，差距来自 **TLE 描述符 DMA + `[XBLOCK]` 流式归约 + 主 tile 无 mask**；如果要把 softmax 从 409 µs 拉到 ~167 µs，需要按这个结构重写（仍需 `tle.gpu`，属于较大改造）；
3. **我们的 layernorm 已经优于 FlagGems 参考**（215 vs 495），但都远慢于 eager（49.6）——按文档走 SM 写回是更值得尝试的方向；
4. **matmul 参考 kernel 碰撞编译器**（LLVM 22 断言），说明 FlagGems 与本工具链版本不完全匹配；其 **tile/warps 规则仍可借鉴**，但需在我们自己的 kernel 上验证；
5. exp2 的写法、`do_not_specialize`、warp 启发式、坏 tile 32768 等是可以直接吸收的小改动。

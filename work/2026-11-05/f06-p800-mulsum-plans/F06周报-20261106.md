## 五、两个后端 issue 与当前解决方法

### Issue 1：bf16 pointwise 在 XBLOCK > 1024 时输出欠写

- **现象**：bf16 逐元素核在 `XBLOCK=2048/3072/4096` 时，正确元素比例恰为 `1024/XBLOCK`
  （50% / 33% / 25%），其余输出保持未初始化内存，bf16 下常表现为散落的 `inf`（`0x7F80`）。
- **根因**：大 tile 配置编译失败（`OutOfResources: out of resource: uni_sram`）后，launcher
  静默回落到基准 tile（1024），但 grid 仍按请求的 XBLOCK 计算 → 只写 `grid×1024` 个元素。
- **当前解决方法**：bf16 输入时把 XBLOCK 限制在 1024，并关闭 coordinate-descent 搜索；
  实测恢复 100% 正确、0 个非有限值。该守卫只影响 bf16，其它精度不受影响。
- **根修建议**：fallback 时同步重算 grid，或让 bf16 tile 在 SRAM 预算内成功编译。

### Issue 2：`f32 → bf16 → f32` 的 cast 被折叠为恒等

- **现象**：`v.to(tl.bfloat16).to(tl.float32)` 不产生舍入（值原样返回）；同样写法换成 `f16` 则正确；
  把 f32 存进 bf16 张量也能正确舍入。
- **根因**：XPU3 没有 bf16 转换指令，后端把“bf16 只在 LM 边界转换”作为设计，寄存器级的
  `truncf/extf` 被视为恒等而折叠，导致依赖它做舍入的核（包括 Inductor 自己生成的 bf16 核）
  都静默丢失舍入。
- **当前解决方法**：在需要 bf16 舍入的核里改用手工 RNE 位运算
  （`bits + 0x7FFF + ((bits>>16)&1)`，再取高 16 位），可完全复现 PyTorch 语义，代价约 +65 µs。
  本周 bf16 不启用，即基于此权衡。
- **根修建议**：在 lowering 中把寄存器级 `f32→bf16` 下降为软件 RNE 序列
  （参考 GPU 的 `cvt.rn.bf16.f32`）。

## 七、为什么相对 eager 没有优势（实测拆解，2026-11-06 09:00）

Mul+Sum 2048×2048 FP32，把两条路线拆到 kernel 级别（152 卡 2，空闲）：

| 组成 | 耗时 | 等效带宽 |
|---|---:|---:|
| eager `mul`（厂商 kernel） | **22.4 µs** | ~1.4 TB/s |
| eager `sum`（厂商 kernel） | 12.8 µs | — |
| eager 两步合计 | **~35 µs** | — |
| 普通 Triton 一维逐元素 mul（BLK=8192，最好） | 50.6 µs | ~0.63 TB/s |
| 普通 Triton 二维 tile 融合 mul+sum（最好 64×128） | 107.5 µs | ~0.15 TB/s |
| 我们的 dsa 归约核（单核） | 22.2 µs | — |

结论：

1. **差距来自 Triton 在本后端的代码生成质量，不是融合策略**：同样的逐元素乘法，厂商 eager kernel
   22.4 µs，普通 Triton 一维写法 50.6 µs（2.3×），二维 tile 写法 107.5 µs（4.8×）。
2. 我们把归约做快了（dsa 22 µs，接近 eager 的 sum 12.8 µs），但**乘法仍然由 Triton 生成**（约 40–50 µs），
   所以整条路线 72.8 µs > eager 35 µs。
3. 这也解释了“vs Inductor 有 1.4–4.9×、vs eager 只有 0.7–1.0×”：Inductor 生成的是更慢的 Triton 核，
   而 eager 直接用厂商高度优化的算子。**要真正超过 eager，必须用厂商算子（xblas/XMLIR）或 dsa 通路承担乘法**，
   单靠改进 Triton 模板达不到。

说明与解读：

1. **只有 MatMul+epilogue 两类（ReLU、GELU-exact）在 e2e 口径下真正快于 eager**（1.10–1.27×），
   因为它们把 bias/激活融进厂商 matmul 的 epilogue，省掉一到两次全张量往返。
2. **Add+Softmax / Add+LayerNorm 与 eager 基本持平**（0.97–1.03×）：融合省下的多趟访存，
   刚好抵消 Triton 单核效率低于厂商 kernel 的差距。
3. **Mul+Sum、Add+GELU/SiLU 低于 eager**（0.84–0.92×）：这类模板本身就是单趟逐元素/归约，

4. 今日抽查里 Add+Softmax 的 0.12× 是我们能跑的“原生单核路线”，不是 11-03 用的 F06 softmax 模板
   （该模板路径在 152 上无法运行，见第四节说明），两者不可直接比较。
5. 因此对外表述建议：**相对 Inductor 的加速比要配“相对 eager”一起看**——只有 MatMul+epilogue
   是“真收益”，归约类模板的收益主要来自“Inductor 在本后端生成的归约核太慢”，而不是融合本身。



## 九、与 11-03 实现的对比：11-03 的 Mul+Sum 更好（重要）

把 11-03 full-v3 的 Mul+Sum 逐形状数据拆出来（FP32，e2e 口径）：

| 形状 | 11-03 vs eager | 11-03 vs Inductor | 今日路线 vs eager | 今日路线 vs Inductor |
|---|---:|---:|---:|---:|
| 16×128 | 0.64 | 1.20 | 0.77 | 1.15 |
| 32×256 | 0.94 | 1.83 | 0.77 | 1.17 |
| 64×1024 | 0.99 | 1.86 | 0.79 | 1.19 |
| **2048×2048** | **1.01** | **3.72** | **0.50** | **2.14** |

结论：**11-03 的融合实现在大矩阵上明显更好**——2048² 时它做到与 eager 持平（1.01×）、相对 Inductor 3.72×；
而本周的整核替换路线是 0.50× / 2.14×，绝对耗时约 70.4 µs vs 11-03 的约 42 µs（按 156.7/3.72 反推）。

原因分析：

1. 11-03 走的是 F06 的 `mul_sum` 融合模板（单核、平铺布局、带选参），命中我们测得的“一维平铺”高效写法；
2. 本周的整核替换路线（cluster 乘 + dsa/plain 归约）**先把乘积物化成 16MB 中间张量**，多了一次全量读写，
   且乘法仍是 2D tile 的 Triton 核（我们实测其带宽只有厂商 kernel 的 15%–45%）；
3. 因此本周在 Mul+Sum 上的“优化”相对 11-03 实际是**退步**。

建议：

- **默认路线恢复为 11-03 的融合实现**，本周的整核替换只保留为“F06 路径不可用时的兜底”；
- 本周真正有价值的产出是：两个后端缺陷（bf16 欠写、bf16 cast 折叠）的定位与规避、
  以及大矩阵多路线对比数据（解释“相对 Inductor 高、相对 eager 低”的原因）；
- 下周应把“一维平铺 + 块内归约”的单核写法做进 Mul+Sum 模板，目标追平 11-03 的 1.01×（而不是当前的 0.50×）。

## 十一、更正：11-03 的“更好”其实是 eager 回退（2026-11-06 09:05）

对 11-03 full-v3 的逐用例数据做进一步核对（`routes.auto.gpu_us` vs `routes.eager.gpu_us`）：

| 模板（2048×2048，FP32） | auto | eager | inductor |
|---|---:|---:|---:|
| MatMul + Bias + ReLU | 211.3 µs | 211.3 µs | 240.0 µs |
| Add + Softmax | 75.3 µs | 75.3 µs | 849.2 µs |
| Add + LayerNorm | 49.6 µs | 49.7 µs | 335.0 µs |
| Mul + Sum | 35.6 µs | 35.5 µs | 160.2 µs |

**auto 与 eager 完全相等**，说明 11-03 在这些大矩阵用例上**没有真正融合，而是回退到 eager**。
全量统计（216 用例，按 auto/eager 是否在 ±3% 内判定）：

| 形状类别 | 回退到 eager | 真正融合 |
|---|---:|---:|
| 小矩阵（≤64×1024） | 76 | 32 |
| 大矩阵 | 85 | 23 |

结论修正：

1. 之前第九节“11-03 的 Mul+Sum 更好（1.01× vs eager、3.72× vs Inductor）”的表述**不准确**：
   那组数字等价于“eager vs Inductor”，因为 auto 就是 eager。
2. 11-03 相对 Inductor 的高倍率（3.7–9×）主要反映 **Inductor 在 P800 上生成的归约核很慢**，
   而不是 F06 融合的功劳；真正融合的用例只占 55/216。
3. 本周的 Mul+Sum 整核替换（0.50× vs eager）确实不如“直接用 eager”，但与 11-03 的“auto=eager”相比，
   差别只是我们多花了 35 µs 的中间张量物化；**两者都没有超过 eager**。
4. 因此“默认恢复为 11-03 路径”的实际含义是：**大矩阵直接用 eager 回退**，融合只在小矩阵生效。


## 十二、融合到底有没有用：按模板拆开看（11-03 全量数据的再分析）

“全是回退”不准确。把 11-03 的 216 个用例按“auto 与 eager 是否一致”分类后，真正融合的用例
（55 个）的收益如下（相对 eager 的 GPU 加速比）：

| 模板 | 小矩阵：融合用例数 / 中位加速比 / 最好 | 大矩阵：融合用例数 / 中位加速比 / 最好 |
|---|---|---|
| MatMul + Bias | 6 / **2.24×** / 2.51× | 4 / 1.87× / 2.00× |
| MatMul + Bias + ReLU | 6 / **2.84×** / 3.38× | 4 / 2.11× / 2.27× |
| MatMul + Bias + GELU（exact） | 5 / 2.24× / 2.32× | 6 / 1.88× / 2.55× |
| MatMul + Bias + GELU（tanh） | 1 / 1.54× | 6 / 1.49× / 1.63× |
| MatMul + Bias + SiLU | 4 / 1.99× / 2.34× | 3 / 1.23× / 1.54× |
| Mul + Sum | 5 / 1.40× / 1.97× | 0（全部回退） |
| Mul + Sum（keepdim） | 5 / 1.40× / 1.97× | 0（全部回退） |
| Add + Softmax | 0 | 0 |
| Add + LayerNorm（4 个变体） | 0 | 0 |
| Add + GELU / Add + SiLU（3 个变体） | 0 | 0 |

结论：

1. **MatMul 系列（5 个模板）是融合的真正收益来源**：几乎全部用例都命中融合，相对 eager
   小矩阵 1.99–2.84×、大矩阵 1.23–2.11×，最好 3.38×。原因是 matmul 走厂商 `extern_kernels.mm`，
   融合只把 bias/激活塞进 epilogue，省掉 1–2 次全张量往返。
2. **Mul+Sum 只有小矩阵能融合（1.40×）**，大矩阵全部回退——这正是本周要解决的问题，
   也说明本周把大矩阵也做到“超过 eager”的目标尚未达成。
3. **Add + GELU/SiLU/Softmax/LayerNorm 全部回退**：这些模板的融合实现要么不可用、要么没有收益，
   最终由选择器回退到 eager。它们“相对 Inductor 3–9×”的数字实际是 eager 自身的优势。
4. 所以正确的对外表述是：**融合在 matmul 系列上有效（1.2–3.4×），在 Add 系列上无效（全回退），
   Mul+Sum 只在小矩阵有效（1.4×）**，而不是“融合没用”。

## 十五、定位：生成的代码和 eager 的差距在哪（2026-11-06 09:55）

以 Add+SiLU 为例，路线最终生成的核（cluster 与 Inductor 完全一致）：

```python
@triton.jit
def triton_unk_fused_0(in_ptr0, in_ptr1, out_ptr0, xnumel, XBLOCK: tl.constexpr):
    x2 = tl.program_id(0) * XBLOCK + tl.arange(0, XBLOCK)
    x0 = x2 % 1024
    tmp0 = tl.load(in_ptr0 + x2)
    tmp1 = tl.load(in_ptr1 + x0, eviction_policy='evict_last')
    tmp2 = tmp0 + tmp1
    tl.store(out_ptr0 + x2, tmp2 * tl.sigmoid(tmp2))
```

**结构完全正确**：a 只读一次、b 广播只读一次、结果只写一次（两趟访存），而 eager 要
`add` 写一次 + `silu` 读一次再写一次（四趟访存）。数据复用确实做到了。

问题在 **XBLOCK**。同一段核，只改块大小：

| 形状 | 路线默认 XBLOCK=1024 | XBLOCK=8192 | eager（add+silu） |
|---|---:|---:|---:|
| 512×1024 | 35.8 µs | **14.7 µs** | 18.8 µs |
| 2048×2048 | 265.3 µs | **78.0 µs** | 72.9 µs |

结论：

1. **同一个融合核，把 XBLOCK 从 1024 调到 8192 快 2.4–3.4 倍**；512×1024 上达到 14.7 µs，
   比 eager 的 18.8 µs 快 **1.28×**——说明“数据复用”本身是有效的，差距来自块大小配置。
2. 现在框架选到的 XBLOCK 是 1024（Inductor pointwise 的默认启发式），远不是最优；这也解释了
   为什么今日实测里大量模板是 0.7–0.8×：代码对、配置差。
3. 2048×2048 上即使 XBLOCK=8192（78.0 µs）仍略慢于 eager（72.9 µs），因为大尺寸下
   Triton 的有效带宽（≈0.4–0.5 TB/s）仍低于厂商 kernel（≈0.9–1.4 TB/s），把“少两趟访存”的优势吃掉了。

**下一步（明确）**：把 Add 系列的 XBLOCK 搜索加进选参（候选 4096/8192/16384），
而不是用 Inductor 默认的 1024；中尺寸（≤512×1024）预计能到 1.2–1.5× vs eager。


## 十六、XBLOCK 优化：实现进展与卡点（2026-11-06 09:40）

已实现（`_resource_codegen.py`）：

1. `FLAGTREE_WIDE_XBLOCK`（默认 1）：对经我们封装的 tuner 增加 4096/8192/16384 候选；
2. `FLAGTREE_FORCE_XBLOCK`：调试用强制块大小；
3. `FLAGTREE_DEBUG_WIDE`：打印实际候选列表。

验证结果：

| 用例 | 改前 | 改后 | eager |
|---|---:|---:|---:|
| Add+GELU(exact) 2048×2048 | 197.0 µs | **172.5 µs** | 253.4 µs |
| Add+SiLU 512×1024 | 28.4 µs | 28.8 µs（无变化） | 21.0 µs |

**卡点（已定位到具体机制）**：`torch._inductor.runtime.triton_heuristics` 在**构造 tuner 时**
（`CachingAutotuner.__init__`）就把 `configs` 编译成固定 launcher 列表；我们在 `decorate(fn)` 之后
再改 `tuner.configs` 不会被采用（调试打印证实候选列表已包含 8192/16384，但运行时仍走原配置）。

**可行的修复路径（下一步）**：在 codegen 阶段直接改写生成源码，给 `@triton_heuristics.pointwise(...)`
显式注入 `configs=[triton.Config({'XBLOCK': 8192}, ...), ...]`（源码会带到 worker 进程，不受
主进程 patch 失效的影响）。这条路径已验证过“源码可改写”（`_p800_special_values` 就是这么做的），
但需要小心处理 bf16 的 XBLOCK 上限。

**归约族**（Softmax/LayerNorm/Mul+Sum）不能靠 XBLOCK：其核为 persistent reduction，
整行 `[XBLOCK, 1024]` 进驻寄存器，实测 462 µs vs eager 27 µs，需要“分块 + 两趟”的新结构。


## 十七、Add 系列优化实现与结果（2026-11-06 10:05）

新增模块 `_p800_flat.py`（整核替换，v1 支持 Add+SiLU/ReLU）并接入 `_resource_runtime.prepare_regions`：
匹配到 `silu(a+b)` / `relu(a+b)` 时发射一维平铺核，XBLOCK 在 1024–16384 间自动搜索并缓存，
其它情况自动回落原生路径。

实测（FP32）：

| 用例 | 替换前 | 替换后 | eager | 相对 eager |
|---|---:|---:|---:|---:|
| Add+SiLU 512×1024 | 28.4 µs | **22.2 µs** | 21.0 µs | 0.73× → **0.95×** |
| Add+SiLU 2048×2048 | 103.4 µs | **78.5 µs** | 72.8 µs | 0.70× → **0.93×** |
| Add+GELU(tanh) 512×1024 | 33.8 µs（原生） | 保持原生 | 42.0 µs | **1.24×** |
| Add+GELU(tanh) 2048×2048 | 118.8 µs（原生） | 保持原生 | 204.0 µs | **1.72×** |
| Add+GELU(exact) 512×1024 | 34.0 µs（原生） | 保持原生 | 41.6 µs | **1.22×** |

两点发现（已写进实现）：

1. **GELU 链在宽块下会触发后端 LLVM 崩溃**：`LLVM ERROR: SmallVector unable to grow. Requested capacity (4294967296)`，

2. **SiLU 的剩余差距是每调用开销**：核本身 14.7 µs，路线 22.2 µs，差额约 7.5 µs 是 Python/分配开销；
   要达到 1.0× 以上需要把调用开销再压下去（例如复用输出缓冲或走 CUDA Graph）。

归约族（Softmax/LayerNorm/Mul+Sum）仍需要“分块 + 两趟”的新核结构，本轮未完成。


## 十八、归约族改造结果（2026-11-06 10:20）

新增 `_p800_reduce.py`（整核替换，v1 支持 `(a*b).sum(-1)`、`layer_norm(a+b)`，softmax 因后端限制暂不替换），
核形态 = **按行分块 + 按列分块的两趟循环**（每次只驻留 `[R, C]` ≤ 8KB，避免 `uni_sram` 溢出），
R/C/warps 自动搜索并缓存，失败自动回落原生。

实测（FP32，512×1024）：

| 模板 | 改造前（原生） | 改造后 | eager | 相对 eager |
|---|---:|---:|---:|---:|
| Add + LayerNorm（无仿射） | 462.2 µs | **61.6 µs** | 27.1 µs | 0.06× → **0.44×** |
| Mul + Sum | 148.3 µs | **43.7 µs** | 20.6 µs | 0.14× → **0.47×** |
| Add + Softmax | 525.7 µs | 保持原生 | 20.9 µs | 0.04×（无改善） |

结论：

1. **分块两趟写法把归约族从“慢一个数量级”拉到“慢 2–2.5 倍”**：LayerNorm 462→61.6 µs（7.5×）、
   Mul+Sum 148→43.7 µs（3.4×），但离 eager 仍有 2~2.5 倍差距（Triton 访存效率所限）。
2. **Softmax 无法编译**：即便 `[2,128]`（1KB）也报 `OutOfResources: uni_sram`，说明后端对多趟 exp 链的
   SRAM 估算过高；v1 保留原生路径，实际运行由选择器回落到 eager（20.9 µs），不会比现在更差。
3. 所有替换都有自动回落；默认开启由 `FLAGTREE_FLAT_REDUCE=1` 控制。

**剩余工作**：Softmax 需要后端支持（或单趟 online-softmax 写法再试）；要追平 eager 仍需解决
Triton 在本后端的访存效率（0.4–0.6 TB/s vs 厂商 0.9–1.4 TB/s）。


## 十九、归约族与 eager 生成产物的差距分析（2026-11-06 10:30）

我们看的是“访存效率”，因为归约类算子的算术量可以忽略。按实际数据量折算有效带宽：

| 用例 | 我们的核 | 我们访存 | 我们带宽 | eager | eager 访存 | eager 带宽 |
|---|---:|---:|---:|---:|---:|---:|
| Mul+Sum 512×1024 | 43.7 µs | 2 MB（1 趟） | **0.05 TB/s** | 21.0 µs | 6 MB（3 趟） | 0.29 TB/s |
| Mul+Sum 2048×2048 | 188.6 µs | 16 MB（1 趟） | **0.09 TB/s** | 35.4 µs | 48 MB（3 趟） | **1.35 TB/s** |
| LayerNorm 512×1024 | 41.1 µs | 6 MB（3 趟） | 0.15 TB/s | 27.3 µs | 10 MB（5 趟） | 0.37 TB/s |

**结论：我们的访存趟数只有 eager 的 1/3，但有效带宽只有它的 1/17–1/3，所以总时间是它的 2–5 倍。**

为了排除“tile 选得不好”，我们把能试的都试了（同一 2048² Mul+Sum）：

| 配置 | 耗时 | 带宽 |
|---|---:|---:|
| R=1, C=2048（整行连续） | 226.0 µs | 0.07 TB/s |
| R=2, C=2048（整行连续） | 213.3 µs | 0.08 TB/s |
| R=8, C=256（分块） | **188.6 µs** | 0.09 TB/s |
| 加 num_stages=2/4（流水） | 189.8–230.6 µs | 0.07–0.09 TB/s |

也就是说：**tile 形状、整行连续、流水线都不是原因**——Triton 的普通 load 在归约形态下只能跑到 0.05–0.09 TB/s，
而厂商 eager kernel 跑到 1.35 TB/s。唯一在 Triton 侧能跑快的访存通路是 **TLE/dsa 的 2D DMA**（实测 0.7 TB/s），
但它无法与厂商的融合归约竞争（dsa 归约 22 µs + 乘法 22.4 µs ≈ 45 µs > eager 35 µs）。

**因此结论是**：归约族（Mul+Sum / LayerNorm / Softmax）在当前后端上**无法超过 eager**，
最优策略就是“融合不可用时回退 eager”——这也正是 11-03 全量测试中观察到的行为。
本周把原生路径从 0.06–0.14× 提升到 0.44–0.47×（LayerNorm 7.5×、Mul+Sum 3.4×），
在不改变“最终回退 eager”结论的前提下，显著缩小了万一必须用自研核时的差距。

## 二十三、最终产物与 eager 的逐项差距定位（2026-11-06 11:20）

把最终产物（我们生成的核）和 eager 的执行方式逐项拆开，差距只有四个来源：

### 1. 访存趟数：我们赢

| 用例 | eager 的核 | 我们的核 | 趟数比 |
|---|---|---|---:|
| Mul+Sum | `mul`（读+写）+ `sum`（读）= 3 趟 | 单核 DMA 读 1 趟 + 写 (m,) | 1 : 3 |
| Mul+Sum keepdim | 同上 | 同上 | 1 : 3 |
| LayerNorm | `add`（读+写）+ `layer_norm`（读+写，含两次归约）= 4–5 趟 | 2 趟（sum/sumsq 合一 + 写） | 2 : 5 |
| Add+SiLU | `add` + `silu` = 4 趟 | 1 趟读 + 1 趟写 | 2 : 4 |
| Add+GELU | 同上 | 同上（保留原生） | 2 : 4 |

### 2. 有效带宽：我们输（这是主因）

| 通路 | 带宽 |
|---|---:|
| 厂商 eager（DMA + 大块连续） | 0.9–1.35 TB/s |
| 我们的 dsa 单核（Mul+Sum 大尺寸） | 0.50–0.52 TB/s |
| 我们的 flat 核（LayerNorm/SiLU） | 0.15–0.18 TB/s |
| 我们的原生 Triton 归约 | 0.05–0.09 TB/s |

**净效果**：Mul+Sum 2048² 上我们搬 1 趟（16MB）用 31.7 µs（0.50 TB/s），eager 搬 3 趟（48MB）用 35.5 µs（1.35 TB/s）——
**用 1/3 的字节数换 2.7 倍的带宽劣势，净赢 1.12×**。这解释了为什么只有大尺寸能赢：尺寸越大，趟数优势越能覆盖带宽劣势。

### 3. 每次调用的固定开销：小尺寸输在这

16×128 这类小形状上，核本身只要 2–3 µs，但：

| 路径 | 单次调用耗时 |
|---|---:|
| eager（2 个 aten 调用） | 21–23 µs |
| 我们的路线（fx 包装 + 区域闭包 + 可选 tile 查表） | 25–27 µs |

固定开销比 eager 多约 4–6 µs，这是小尺寸 0.86–0.92× 的全部来源（kernel 本身并不慢）。

### 4. 结构性限制（无法靠调优解决）

| 限制 | 影响 |
|---|---|
| 片上缓冲上限 ≈ 8KB | 大尺寸 Softmax/LayerNorm 的核编不出来（`uni_sram`），回落原生 → 0.09–0.17× |
| dsa 仅支持 FP32 快路径（16 位寄存器级转换慢） | FP16 大尺寸只能走 flat 核 → 0.15× |
| F06 框架把 weight/bias 作为 `get_attr` | 仿射 LayerNorm 无法接入 → 0.05–0.47× |

**一句话**：**趟数我们已经赢，赢不回来的只有“每字节带宽”和“固定调用开销”**；大尺寸趟数优势足以翻盘（1.08–1.12×），
小尺寸则被 4–6 µs 固定开销吃掉；而 Softmax/大尺寸 LayerNorm/FP16 大尺寸/仿射这四类是结构限制，不在调优范围内。


## 二十四、带宽与固定开销的最终优化结果（2026-11-06 11:35）

### 带宽：dsa 的 DMA 上限已探到

按“厂商 DMA + 大块”方向把 dsa 的 2D tile 继续加大：

| tile | 耗时（2048² Mul+Sum） | 带宽 |
|---|---:|---:|
| 64×256 | 32.1 µs | 0.52 TB/s |
| **64×512** | **32.9 µs** | **0.51 TB/s** |
| 64×1024 | 47.0 µs | 0.36 TB/s |
| 32×1024 | 41.0 µs | 0.41 TB/s |
| 128×512 | 54.8 µs | 0.31 TB/s |

结论：**0.52 TB/s 是 dsa 在当前后端的带宽上限**，再大反而变差（片上 staging 效率下降）。
尝试让 dsa 核走 cluster（64 核）路径也失败（`uni_sram`），说明 dsa 只能在 SDNN 路径运行——
这很可能就是“厂商 1.35 TB/s vs 我们 0.52 TB/s”约 2.6 倍差距的来源（SDNN 可用核心数少于全芯片）。

### 固定开销：已削减约 3–4 µs

把 `_p800_dsa` 的每次调用路径重写为“首次调用建好 launcher 闭包，之后只做 shape 校验 + 分配 + 启动”，
去掉每调用的 env 查询、dict 查找与参数拼装：

| Mul+Sum 2048×2048 FP32 | 31.7 µs | **31.7 µs** | 34.8 µs | **1.10×** |
| Mul+Sum keepdim 2048×2048 | 31.8 µs | **31.8 µs** | 34.9 µs | **1.10×** |

剩余固定开销约 3–5 µs（分配输出 + fx 层 + 启动），已接近 eager 的 2 个 aten 调用开销。

## 二十五、厂商带宽为什么高：逐层定位（2026-11-06 11:50）

在同一张卡、同一数据量（2048×2048 fp32，读+写 32MB）下比较不同通路的**纯带宽**：

| 实现 | 耗时 | 带宽 |
|---|---:|---:|
| 厂商 `copy_` | 18.2 µs | **1.84 TB/s** |
| 厂商 `mul` | 22.4 µs | 1.50 TB/s |
| 厂商 `add` | 22.7 µs | 1.48 TB/s |
| **Triton 1D copy，BLK=8192** | 31.5 µs | **1.06 TB/s** |
| Triton 1D copy，BLK=4096 | 56.0 µs | 0.60 TB/s |
| Triton 1D copy，BLK=1024 | 205.1 µs | 0.16 TB/s |
| Triton 1D add（`i % P` 广播），BLK=8192 | 50.7 µs | 0.66 TB/s |
| Triton dsa DMA（SDNN） | — | 0.52 TB/s |
| 原生 Inductor 归约（多趟） | — | 0.05–0.09 TB/s |

**差距可以精确分解成三层：**

1. **厂商 vs Triton 最好情况**：1.84 vs 1.06 TB/s，约 **1.7×**。这部分是向量化宽度与占用率
   （厂商 kernel 用 128-bit 向量访存、满 64 核；Triton 后端即使 BLK=8192 也只能到 1.06）。
2. **块大小**：同一个 Triton copy，BLK 从 1024 加到 8192，带宽 **0.16 → 1.06 TB/s（6.6×）**。
   而 Inductor 的 pointwise 公式把 XBLOCK 固定在 ≤1024 —— 这就是我们默认路线只有 0.15–0.18 TB/s 的主因。
3. **广播索引**：带 `i % P` 的 add 只能到 0.66 TB/s（比 copy 低 1.6×）；用二维行块（`r[:,None]*N + c`）
   本可去掉 modulo，但该写法在当前后端触发向量化器 bug：
   `tt.expand_dims op operand #0 must be ranked tensor ... but got 'tensor<64xvector<16xf32>>'`，
   或撞 `uni_sram` 上限，所以暂时无法落地。

**结论**：厂商的高带宽 = 128-bit 向量化 + 满核占用；Triton 在**纯 1D、大块、无广播**时能到 1.06 TB/s
（只差 1.7×），但被三件事拖回 0.15 TB/s：Inductor 的 1024 块上限、广播 modulo、以及二维行块写法
触发的后端向量化 bug。要接近厂商带宽，必须同时解决这三层；目前只解决了“大块”的候选（但被
Inductor 的公式卡住）。


## 二十六、能否复用厂商接口实现高带宽：实测结论（2026-11-06 12:05）

### 可用的厂商接口盘点

| 接口 | 可用性 | 结论 |
|---|---|---|
| torch eager 算子（mul/add/sum/layer_norm） | 可用 | 调它就等于不融合，已排除 |
| XBLAS | 仅 matmul | 与 Add/Reduce 无关 |
| XTDK DMA（GM2SM/SM2GM） | 只能通过 `tle.dsa` 使用（SDNN 路径） | 已用，实测上限 **0.52 TB/s** |
| 设备端 SIMD intrinsics / inline asm | Triton XPU 后端未开放 | 无法调用 |

### Triton 自身的内存上限（实测）

| 操作（2048²，BLK=8192） | 耗时 | 备注 |
|---|---:|---|
| 1D copy | 31.8 µs | **1.06 TB/s**，Triton 最好情况 |
| 双流 add（两个完整张量） | 37.5 µs | 1.28 TB/s（48MB） |
| **sigmoid** | **76.1 µs** | 与 copy 同流量，慢 2.4× |
| **silu** | 74.3 µs | — |

**关键发现：Add+SiLU 是算力受限，不是带宽受限。** 4M 个元素的 sigmoid 本身要 ~44 µs，
厂商 eager 的 silu 同样慢（add 22.7 + silu ≈50 µs），所以这个模板“融合 vs eager”最多打平——
再优化访存也没有意义。

### 预展开 b（去掉 modulo）的尝试：无收益

| 方案 | 512×1024 | 2048² | 流量 |
|---|---:|---:|---|
| `i % P` 广播 | 15.3 µs | 78.4 µs | 2 流 |
| 预展开 b + 纯 1D | 14.9 µs | 77.3 µs | 3 流 |

两者耗时相同（预展开多吃 16MB 流量、换来更高效率），净收益为零，已放弃。

### 最终定性

1. **访存密集型**（Mul+Sum、LayerNorm、keepdim）：已用 dsa DMA + 减少趟数拿到 1.08–1.12×（大尺寸）；
   剩余差距是 SDNN 0.52 vs 厂商 1.35–1.84 TB/s，属于执行引擎差异。
2. **算力密集型**（Add+SiLU/GELU）：sigmoid/exp 占总耗时 60%，融合只能省访存、省不掉算力，
   最终与 eager 打平（0.9–1.1×）。
3. **Triton 纯内存天花板**是 1.06 TB/s（1.7× 于厂商 1.84），要到 1.8 需要 128-bit 向量化，
   这层后端不开放，无法从 Triton 侧复现。


## 二十七、能否把厂商高带宽封装成一个接口：结论与建议（2026-11-06 12:20）

### 现状：三层的接口/带宽

| 层 | 可用接口 | 实测带宽 | 能否计算 |
|---|---|---:|---|
| 宿主侧 | `Tensor.copy_` / memcpy | **1.84 TB/s** | ❌ 只能搬运 |
| 厂商计算核 | torch eager 算子 | 1.48–1.50 TB/s | ✅（但不能融合） |
| Triton 普通访存 | `tl.load/tl.store`（1D，大块） | **1.06 TB/s** | ✅ |
| Triton DMA 通路 | `tle.dsa.copy`（SDNN） | 0.52 TB/s | ✅ |

补充实测：Triton 的 1D copy 在 BLK ≥ 8192 后**饱和在 1.06 TB/s**（8192/16384/32768 与 warps 8/16 全部 1.04–1.06），
再大也不涨——说明瓶颈不是块大小，而是**访存位宽**（Triton 后端发出的是窄向量，厂商 kernel 用 128-bit）。

### 为什么不能直接“封装成一个接口”

1. 厂商的高带宽接口是**面向搬运**的（`copy_`），不对外提供“搬运 + 计算”的组合原语；
2. 厂商的计算核（mul/add）已经内置了 128-bit 向量化 + 满核调度，但它只以**框架算子**形式暴露，
   调它就等于不融合（我们实测“厂商乘 + dsa 归约”= 45 µs > eager 35 µs）；
3. Triton 侧能调用的唯一设备级搬运接口是 `tle.dsa`，它的 DMA 带宽只有 0.52 TB/s，
   反而低于 Triton 普通 1D 大块访存的 1.06 TB/s，不适合做通用数据通路；
4. 真正的差距在**后端代码生成**（位宽），不在“缺一个 API”。

### 建议向后端/厂商提的接口（可直接落地）

1. **向量化访存原语**：让 TLE 暴露 `tle.dev.load_vec/store_vec(ptr, dtype, width=128)`，
   由 Triton 直接下发 128-bit 访存指令（对标厂商 kernel 的位宽）。预期把 Triton 的 1.06 拉到 ~1.5–1.8 TB/s。
2. **异步 2D 拷贝 + 双缓冲**：`tle.dsa.copy_async(dst, src, sizes=[R, C], stages=2)`，
   让归约核在 SDNN 上能重叠“搬下一块”和“算当前块”，预期把 0.52 TB/s 提到接近 DMA 理论值。
3. **修复二维/广播向量化**：当前 `r[:, None]*N + c` 写法会触发
   `tt.expand_dims ... got 'tensor<64xvector<16xf32>>'` 的向量化器错误（`TritonXPUVectorize`），
   这也是广播类模板无法用高带宽写法（去 modulo）的直接原因。

### 我们这边还能做的（不依赖厂商）

- 把元素级模板统一成“1D 大块 + 无广播”写法（需框架支持 b 的扁平视图，或接受预展开 b 的额外流量）；
- 归约族继续用 dsa（0.52 TB/s）+ 减少趟数，已拿到 1.08–1.12×；
- 算力密集型模板（SiLU/GELU）不再追求带宽优化，改为**算子层面减少调用次数**。


## 二十八、Add+SiLU 的算力受限点定位（2026-11-06 12:35）

同一张量（2048×2048 fp32，16MB 读 + 16MB 写）下逐个拆解：

| 核 | 耗时 | 相对 copy 的算术成本 |
|---|---:|---:|
| Triton copy（纯访存） | 32.6 µs | — |
| Triton `exp` | 69.8 µs | **+37.2 µs** |
| Triton `sigmoid`（1/(1+exp(-x))） | 76.6 µs | **+44.0 µs** |
| 厂商 `sigmoid` | **48.8 µs** | **+16.2 µs** |
| 厂商 `silu` | **50.9 µs** | **+18.3 µs** |
| 我们融合的 add+silu | ~74–78 µs | — |

**结论：算力受限点就是 `exp` 的 lowering。**

- 我们一次 sigmoid 的算术开销约 **44 µs**，厂商同类只有 **16 µs**，相差 **2.7×**；
- 也就是说 SiLU 的 78 µs 里，约 32 µs 是访存、44 µs 是 exp 计算，而厂商只需要 ~16 µs 的 exp；
- 即使我们把 exp 优化到厂商水平，融合后的 SiLU 也只有 ~50 µs，与厂商 50.9 µs 持平——**这就是“融合在算力受限模板上最多打平”的量化依据**。

尝试过的替代路径与结果：

| 尝试 | 结果 |
|---|---|
| `tl.math.exp2(x * log2e)` | 58.6 µs（快 11 µs）但**结果错误**（err 1078），说明后端 exp2 lowering 有缺陷 |
| exp2 版 sigmoid | 74.7 µs，误差 0.08（不可用） |
| exp2 版 silu | 137.3 µs（更慢），误差 0.13（不可用） |

因此 Add+SiLU 的下一步不是继续调访存，而是**推动后端把 exp 降低为硬件指令/快速多项式**（对标厂商 16 µs 的算术开销），
或由后端修复 `exp2` 的 lowering（当前结果错误）。在这之前，Add+SiLU 与 eager 打平就是上限。


## 二十九、SiLU 算力受限的最后验证：三条替代路径都不可行（2026-11-06 12:50）

| 尝试 | 耗时（2048²） | 误差 | 结论 |
|---|---:|---|---|
| `tl.exp` 版 sigmoid（基线） | 76.6 µs | 0 | 算术开销 44 µs |
| `tl.math.exp2` 版 | 74.7–137 µs | 8e-2 ~ 1e3 | **结果错误**（后端 lowering 缺陷） |
| 位运算 fast-exp（多项式 + 2^k 位拼接） | **1265.9 µs** | 8e-5（很准） | **慢 10 倍**，整数/floor 运算在后端被标量化 |
| 厂商 sigmoid | 48.9 µs | — | 算术开销仅 16 µs |

结论：**SiLU 的算力瓶颈只能由后端解决**（把 exp 降为硬件指令/快速多项式）。三条自研替代路径
（exp2、位技巧 fast-exp、预展开 b）全部验证失败或无效，因此 Add+SiLU 与 eager 打平（0.9–1.1×）
就是当前上限，继续在这条模板上做优化不会产生收益。

至此 d 系列模板的优化边界已经全部探明：
- 访存受限（Mul+Sum/keepdim/LayerNorm 部分尺寸）：已拿到 1.08–1.37×；
- 算力受限（SiLU/GELU）：最多打平；
- 其余受后端 SRAM/向量化限制，回退 eager。


## 三十、为什么算术不能复用厂商实现（2026-11-06 13:05）

### 厂商的 exp 是怎么写的（XTDK 手册 3.4 节示例）

```cpp
__global__ void exp_fwd_kl(const T* x, T* y, int64_t len) {
    const int buf_len = 1536;
    __simd__ float local[buf_len];                    // LM 上的 SIMD 缓冲
    partition(tid, nthreads, len, 16, &start, &end);  // 按核分块
    for (i = start; i < end; i += buf_len) {
        GM2LM(x + i, local, read_len * sizeof(T));    // DMA 搬进 LM
        do_cast<T, float>(...);
        primitive_exp<float>(local, local, read_len); // ★ 厂商的 SIMD 数学原语
        do_cast<float, T>(...);
        LM2GM(local, y + i, read_len * sizeof(T));    // DMA 搬回
    }
}
```

关键在 `primitive_exp<float>`：这是**只在 XTDK C++ 设备代码里可用的 SIMD 原语**（对 1536 个 float 的
LM 缓冲做向量化 exp），编译器直接把它映射到硬件数学指令/最优多项式。

### 为什么我们在 Triton 侧拿不到

| 途径 | 结果 |
|---|---|
| 调 `torch.sigmoid/silu`（厂商 kernel） | 等于不融合（多一次 kernel + 一次全量往返），实测 48.9+ 22.7 µs > 融合 |
| 在 Triton 内核里调用厂商设备函数 | Triton 的 XPU 后端不链接 XTDK 的 `primitive_*`，没有 extern 设备函数机制 |
| `tl.exp` 映射到硬件指令 | 由后端 lowering 决定，当前走通用软件路径（44 µs vs 厂商 16 µs） |
| 自己写 fast-exp（位运算） | 精度够（8e-5）但被后端标量化，**1265 µs**（慢 10 倍） |
| `tl.math.exp2` | 结果错误（后端 lowering 缺陷） |

### 想模仿厂商的 DMA 结构也被 API 挡住

尝试按厂商结构写 SiLU（GM→LM DMA、在 LM 上算、LM→GM DMA）：

- `tle.dsa.copy(gm_ptr, buf, sizes=...)` ✅ 可用（搬入）
- 把计算结果写回 buffer 再 DMA 出去 ❌ **XPU 版的 `tle.dsa` 没有 `local_ptr`**（文档里的 `local_ptr`
  只在 Ascend 后端提供），无法对 buffer 做显式 `tl.store`；
- 因此只能“DMA 搬入 + 普通 `tl.store` 搬出”，而 dsa 搬入只有 0.52 TB/s，低于普通大块 load 的 1.06 TB/s，**反而更慢**。

### 结论

1. **算术复用不了**：`primitive_exp` 是 XTDK C++ 设备原语，Triton 后端没有暴露对应接口；
2. **结构模仿也不行**：TLE 的 XPU 侧缺少 buffer 写回 API，DMA 吞吐也低于普通大块访存；
3. 唯一解法是后端把 `tl.exp` 降成硬件 exp（或给 TLE 增加 `tle.dsa.math.exp` 之类的原语）。
   在此之前，Add+SiLU 与 eager 打平（~50 µs vs 50.9 µs）就是上限。


## 三十一、找到厂商数学库源码：`primitive_exp` 与硬件 exp2（2026-11-06 13:30）

不需要反编译——厂商的设备端数学实现以**头文件 + libdevice bitcode** 形式打包在 torch_xmlir/triton 里：

### 1. 厂商头文件里的实现

`torch_xmlir/include/xpu/kernel/cluster_primitive.h`：

```cpp
template <> __device__ void primitive_exp(const float* x, float* y, int len) {
    for (int i = 0; i < rounddown4(len); i += 4) {
        float v0 = x[i+0]; ... float v3 = x[i+3];
        y[i+0] = exp(v0); ... y[i+3] = exp(v3);      // 展开 4 路
    }
}
```

它只是**手工展开 4 路 + 普通 device `exp`**；真正快的是 `cluster_math.h` 里的编译器内建：

```cpp
__builtin_xpu_exp2f   __builtin_xpu_log2f   __builtin_xpu_mulf
__builtin_xpu_sqrtf   __builtin_xpu_fdiv_rn
```

厂商的 `pow` 就是 `log2 → mul → exp2`，即 **exp 走硬件 exp2 指令 + 乘 log2e**。

### 2. libdevice 里确实有这些符号

`triton/backends/xpu/xpu3/lib/libdevice-xpu3.bc` 的字符串里可以看到：

```
_ZN3xpu5exp2fEf          xpu::exp2f(float)
_ZN3xpu8xpu_expfEf       xpu::xpu_exp(float)
_ZN3xpu9vsigmoidfEDv16_f xpu::vsigmoidf(16 宽 float 向量)   ← 向量版 sigmoid
llvm.xpu.exp2f / llvm.xpu.log2f / llvm.xpu.mulf             ← 硬件内建
```

### 3. Triton 侧为什么用不上

| 尝试 | 结果 |
|---|---|
| `tl.exp` | 算术开销 44 µs（厂商 16 µs） |
| `tl.math.exp2` | 结果错误（err 1078） |
| `triton.language.extra.libdevice.exp2` | 能编译但 **13625 µs**（13.6 ms！比 tl.exp 慢 180 倍），说明 LLVM 把 libdevice 的 exp2 当普通函数调用、没落到 `llvm.xpu.exp2f` |
| 直接 extern_elementwise 调 `_ZN3xpu5exp2fEf` | 编译失败（`_semantic argument must be provided outside of JIT functions`，Triton 3.6 的用户级 extern 限制） |

### 4. 后端补丁（唯一可行路径，已定位到行）

`third_party/xpu/lib/Conversion/TritonXPUToLLVM/ElementwiseOpToLLVM.cpp:192`：

```cpp
POPULATE_UNARY_OP(math::ExpOp, LLVM::Exp2Op)   // 直接映射，未走厂商内建
POPULATE_UNARY_OP(math::LogOp, LLVM::Log2Op)
```

参照同文件里已有的范式：

```cpp
patterns.add<OpToExternCallConversion<triton::PreciseSqrtOp>>(
    typeConverter, axisInfoAnalysis, "_ZN3xpu10__fsqrt_rnEf", benefit);
```

应改为把 `math::ExpOp / math::Exp2Op` 降成对 `_ZN3xpu5exp2fEf`（或向量版 `_ZN3xpu9vsigmoidfEDv16_f`）的 extern 调用，
并修正 exp 的 log2e 缩放。预期可把 Add+SiLU 的算术开销从 44 µs 降到 ~16 µs，融合后约 50 µs（与 eager 持平或略优）。


## 三十二、直接调用厂商 libdevice 数学符号的实测（2026-11-06 13:45）

用 `tl.core.extern` + `extern_elementwise` 直接调用 `libdevice-xpu3.bc` 里的厂商符号（无需重建后端）：

| 调用 | 结果 |
|---|---|
| `_ZN3xpu8xpu_expfEf`（xpu::xpu_exp，标量） | 能跑，silu = **137.4 µs**（比 `tl.exp` 的 74.3 µs 还慢） |
| `_ZN3xpu5exp2fEf`（xpu::exp2f，标量） | 能跑但 **15526 µs**（15 ms，libdevice 标量版的 exp2 极慢） |
| `_ZN3xpu5tanhfEf`（tanh） | 能跑，误差 0 |

结论：**厂商的快速数学只在“向量版”符号里**——libdevice 有 `_ZN3xpu9vsigmoidfEDv16_f`
（16 宽 float 向量的 sigmoid）、`vsinf/vcosf/vtanhf/verf` 等，全部是 `Dv16_f`（16 宽向量）签名；
标量版本比 Triton 自带的还慢。

而 Triton DSL 无法构造 16 宽向量类型去调 extern 函数——这些向量类型是**后端 vectorizer 在 lowering
阶段内部生成的**。所以：

- 想用上厂商快速数学，**必须改后端**：在向量化之后把 `math.exp2`/`sigmoid` 的标量调用替换成
  `llvm.xpu.exp2f` 或向量 libdevice 符号；
- 纯 Python/DSL 层无解（已用三种方式验证：`tl.math.exp2`、`libdevice.exp2`、`extern_elementwise`）。

这也是 Add+SiLU 模板的最终技术结论：**算力差距（44 vs 16 µs）只能由后端补丁消除**，
补丁位置已定位到 `ElementwiseOpToLLVM.cpp:192`，参照同文件 `PreciseSqrtOp → _ZN3xpu10__fsqrt_rnEf`
的 extern 调用范式，并配合向量化路径使用 `Dv16_f` 向量符号。

## 三十四、全模板检查：哪些能靠接入厂商库加速（2026-11-06 14:15）

按“该模板的关键路径是否依赖超越函数（exp/tanh/erf/rsqrt）”逐一核对：

| 模板 | 关键超越函数 | 当前 vs eager | 厂商库可带来加速 | 说明 |
|---|---|---|---:|---|
| MatMul + Bias | 无 | 0.95 | ❌ | matmul 已走厂商 extern mm |
| MatMul + Bias + ReLU | 无 | 1.12 | ❌ | — |
| MatMul + Bias + GELU（exact） | erf | 1.27 | ⭕ 小 | epilogue 的 erf 可用 `xpu::erf` 向量版 |
| MatMul + Bias + GELU（tanh） | tanh | 0.99 | ⭕ 小 | 同上（`vtanhf`） |
| MatMul + Bias + SiLU | sigmoid(exp) | 0.92 | ⭕ 中 | epilogue 的 exp |
| Add + Softmax | exp（3 趟） | 0.09–1.10 | ✅ **大** | 3 趟 exp，44→16 µs 意味着省 ~84 µs |
| Add + GELU（exact/tanh） | erf/tanh | 1.21–1.71 | ⭕ 小 | 已领先，锦上添花 |
| Add + SiLU | sigmoid(exp) | 0.93–1.13 | ⭕ 中 | FP32 2048² 受 exp 限制（0.93×） |
| Add + LayerNorm | sqrt/rsqrt | 0.17–1.37 | ❌ | rsqrt 只占极小比例 |
| Mul + Sum / keepdim | 无 | 0.84–1.12 | ❌ | 纯访存 |

补充实测：自己写的融合 softmax 核（3 趟分块 + `tl.exp`）最好只有 **772.8 µs**（R=8, C=128），
native 是 462 µs，eager 是 27–73 µs。即 **softmax 的瓶颈完全是 exp**：3 遍全张量 exp，
按当前 44 µs/趟算就要 132 µs，再叠加 3 趟访存，怎么都追不上厂商的向量 exp。

结论：

1. **只有 Add+Softmax 能靠厂商库获得数量级提升**（它的关键路径是 3 趟 exp）；
2. GELU/SiLU 属于“锦上添花”，且仅 FP32 大尺寸有空间；
3. 其余模板（matmul、layernorm、mul_sum）不依赖超越函数，接入厂商库没有收益；
4. 所有“✅/⭕”项都依赖同一个后端补丁（`math::ExpOp → 厂商向量 exp/tanh/erf`），
   所以补丁的优先级应按 **softmax > silu/gelu** 排。


## 三十五、Softmax 的两次融合尝试与最终结论（2026-11-06 14:25）

| 实现 | 结果 |
|---|---|
| 3 趟分块融合（max → exp/sum → exp/write） | 能编译，最好 **772.8 µs**（R8/C128），比 native 462 µs 还慢 |
| 在线 2 趟（flash 式：running max/sum + 写回） | **全部 tile 报 `OutOfResources: uni_sram`**（连 32×64=2KB 都失败） |
| native（Inductor persistent reduction） | 462–525 µs |
| eager（厂商向量 exp） | **27–73 µs** |

在线版本失败位置指向累加器 `s`，说明后端对 online-softmax 表达式的片上缓冲估算过高；
而 native 能编译是因为它用 `[XBLOCK, 整行]` 的 persistent reduction（另一种形态）。

**Softmax 的最终结论**：在 Triton 侧无论用哪种写法都无法接近 eager：
- 3 趟写法受 2×exp（88 µs）+ 3 趟访存限制 → 772 µs；
- 在线 2 趟写法直接编不过（后端 SRAM 估算）；
- 唯一出路仍是后端：**降低 SRAM 估算 + 把 exp 接到厂商向量指令**（预计可到 ~100–150 µs 量级，
  但即便到那时也只是接近而非超过 eager 的 27–73 µs）。

因此 Softmax 保持回退 eager 的策略不变。

## 三十八、二进制层面替换 exp lowering 的可行性分析（2026-11-06 15:20）

既然拿不到厂商源码/预编译对象，评估了“直接改二进制”的路线：

### 可行的部分

- `libtriton.so` 里目标函数是**导出符号**（.dynsym，`T`）：
  ```
  _ZN4mlir6triton3xpu35populateElementwiseOpToLLVMPatternsE...
  ```
  即外部可以调用它；
- 库**没有加 `-Bsymbolic`**（动态段无 SYMBOLIC 标志）。

### 不可行的部分（关键）

用 `readelf -r libtriton.so | grep populateElementwiseOpToLLVMPatterns` 检查重定位：

```
0 条
```

**库内部对它的调用是直接调用（direct call），没有走 PLT**（GCC 对同 DSO 内的定义默认生成直调，不存在 JUMP_SLOT 重定位）。
因此 **LD_PRELOAD 符号替换对它无效**——预加载的同名符号只会影响外部调用者，不影响库内自己的调用。

### 剩下只有两条二进制路线，都不推荐

1. **二进制打补丁**：直接改写 740MB `.so` 中该函数的机器码（把 exp 的 pattern 注册调用改掉）。
   需要反汇编定位 + 精确改指令 + 处理 MLIR C++ ABI，脆弱且不可维护；
2. **独立 MLIR pass 库**：用 apt 的 MLIR 19 编译一个带我们 pattern 的 pass 共享库，
   再通过 `passes.cc` 绑定注入。需要 tablegen 生成 pass 注册头（本机已具备 LLVM/MLIR 头，
   但还需完整跑一遍 incgen），工作量约 1–2 天，收益仍只是 Add+SiLU/Softmax 的 exp。

**结论**：在没有厂商 `modsnn` 预编译对象的前提下，走二进制/符号替换路线成本高于收益；
推荐仍是“拿到 modsnn 后按补丁重建”（工具链已 100% 就绪），或推动厂商把 `tl.exp` 接到向量数学库。

## 四十、如何达到厂商算力：找到硬件指令 exp.f.rn（2026-11-06 17:40）

### 一、厂商的 exp 到底是什么指令

用厂商设备编译器（wheel 里的 `llvm19/bin/clang++ -target xpu3`）编译最小测试：

```cpp
extern "C" float myexp2(float x) { return __builtin_xpu_exp2f(x); }
```

输出 LLVM IR：`%0 = tail call float @llvm.xpu.exp2f(float %x)`
输出汇编：**`exp.f.rn r2, r2`** —— 单条硬件指令。

进一步验证语义：`exp.f.rn` 计算的是**自然 exp**（我们把它做成 Triton inline asm 后与
`torch.exp` 对比，**max_err = 0.0**，完全精确），不是 exp2。

**结论：厂商 16 µs 的算术开销 = 每条元素一条 `exp.f.rn` 硬件指令。**

### 二、为什么在 Triton DSL 层用不上

| 尝试 | 结果 |
|---|---|
| `tl.inline_asm_elementwise("exp.f.rn $0, $1;", pack=1)` | 能编译、结果精确，但 **81.0 µs**（pack=1 破坏向量化） |
| pack=16 打包 asm | 72–74 µs 且**结果错误**（rel_err 32，Triton 的 asm 打包顺序与 XPU 向量寄存器不对齐） |
| 后端把 `VExpFOp → LLVM::Exp2Op` | 软件展开，44 µs 算术开销 |

Triton 的 `inline_asm_elementwise` 走的是标量元素打包，无法映射到 XPU 的 16 宽向量寄存器，
所以 DSL 层拿不到硬件指令的吞吐。

### 三、正确做法（唯一可行路径）

在后端 `VectorizedOpToLLVM.cpp` 里给 `VExpFOp` 增加**基于 inline asm 的向量 lowering**，
照抄同文件已有的 SV 系列范式：

```cpp
SVOp2ASMStrFP16(triton::xpu::SvaddFOp, "vadd.hf.mz.rn $0{mr1}, $1, $2");
```

即把 16 宽 float32 向量的 VExpFOp 拆成 16 个标量 `exp.f.rn $0, $1`（或找到向量形式
`exp.f.rn $0{mr1}, $1`），执行后再打包。这样访存保持向量化、exp 走硬件指令，
预期 Add+SiLU/SiLU 可从 74 µs 降到 **~50 µs（厂商水平）**，sigmoid 从 76 → ~49 µs。

工作量：约半天 C++（需要理解 `VectorizedOpToLLVM.cpp` 的向量寄存器打包工具和
`{mr1}` asm 修饰符用法），之后每次验证只需 3 分钟增量重建（构建链已完全打通）。

### 四、当前状态

- 构建链：✅ 完整可用（源码 + 厂商 SDNN 对象 + LLVM22 + gcc11/sysroot2.17）
- 硬件指令确认：✅ `exp.f.rn`，精确自然 exp

## 四十一、实现硬件 exp 内核 lowering 的尝试与最终结论（2026-11-06 18:30）

### 反汇编揭示的真相

把厂商 libdevice 里 `_ZN3xpu9vsigmoidfEDv16_f`（16 宽向量 sigmoid）用设备编译器展开：

```
vstore_mask16.mz vr0{mr1}, 0(r1)   # 向量寄存器 -> LM 暂存
mfence { lm }
loadli.w r2..r17, ...              # 16 个标量逐个 load
exp.f.rn r2, r2                    # 16 条硬件 exp
...
div.f.rn r2, r1, r2                # 16 条除法
```

**厂商的向量 sigmoid 内部就是 16 条标量 `exp.f.rn`**，没有任何"向量 exp"指令。
所以厂商快的原因不是指令特殊，而是**这条序列被完全内联在 kernel 里、寄存器/LM 由编译器直接安排**。

### 我们实现硬件 exp 的四次尝试

| 方案 | 结果 |
|---|---|
| DSL `inline_asm_elementwise(pack=1)` | 能编译、数值精确，但 **81.0 µs**（破坏访存向量化） |
| DSL `pack=16` 打包 asm | 72–74 µs 且**结果错误**（打包顺序与向量寄存器不对应） |
| 后端 `VExpFOp` 加 inline-asm lowering（extract→16×`exp.f.rn`→insert） | **80.9 µs**（比 baseline 69.5 更慢，extract/insert 开销大） |
| 后端 sigmoid 融合修复（已在之前完成） | 融合生效，但走 libdevice 调用仍是 76 µs |

以上三项实验实现均已回退，baseline 恢复（`triton exp` 69.5 µs、`sigmoid` 76.5 µs）。

### 最终结论：差距在哪

- 厂商 sigmoid：**48.8 µs**（exp 指令内联 + 无函数调用）
- Triton 调 libdevice `vsigmoidf`：**76.5 µs**（同样的 16 条 exp，但有函数调用 ABI：向量值需经 LM 序列化/反序列化）
- 差距 ≈ 27 µs，**全部来自调用/打包开销，不是 exp 指令本身**

要达到厂商速度，唯一途径是在后端把厂商 `vsigmoidf` 的**完整指令序列内联**（含向量→LM 暂存、
16 条 load/exp/div、回写），即"内联向量数学 + LM 暂存分配"。这是一个数天级的编译器工程，
且收益仅限 exp 类模板（Add+SiLU 的大尺寸用例 + Softmax）。

| 形状 | FP32 | FP16 |

| 128×1024 | 1.10× | 1.05× |

## 四十二、不走 TLE 的替代路径评估（2026-11-06 20:20）

组长明确暂不支持 TLE，因此评估并实测了不依赖 TLE 的替代方案。

### 方案 A：纯 Triton 有理逼近 sigmoid（无 exp）——实测不可行

用 Padé [7/6] 逼近 tanh：`sigmoid(x) = 0.5 + 0.5·tanh(x/2)`，纯浮点运算（含 1 次除法），
2048×2048 fp32 实测：

| 指标 | 数值 |
|---|---:|
| tanh 逼近误差（[-4.5,4.5]） | 4.2e-5 |
| sigmoid 最大绝对误差 | 1.21e-4（在容差内） |
| **silu 最大绝对误差** | **1.09e-3（超出 fp32 容差 3e-4）** |
| **pade sigmoid 耗时** | **112.3 µs**（比 `tl.exp` 版 76.5 慢 47%） |
| **pade silu 耗时** | **113.9 µs**（比 74.5 慢 53%） |
| 厂商 silu | 50.7 µs |

结论：**多项式/有理逼近路线不可行**——运算数量换不回 exp 的成本（P800 上除法与多次 FMA 同样贵），
且 silu 在大 |x| 处误差超容差。

### 方案 B：Triton 层 inline asm（pack=1/16）——已测，不可行

- pack=1：数值精确但 81.0 µs（破坏向量化）；
- pack=16：72–74 µs 但结果错误（打包顺序与向量寄存器不对应）。

### 方案 C：后端内联 asm lowering——已测，更慢

`VExpFOp` 用 extract→16×`exp.f.rn`→insert 实现：**80.9 µs**（baseline 69.5），已回退。

### 方案 D：不改数学，改"融合层数" —— 唯一稳妥且仍有收益的方向

Triton 能赢的从来不是单算子算力，而是**减少访存趟数**：

1. **链式融合**：把 add→activation 再往下串（如 add+silu+后续 elementwise）合成一个 kernel，
   每多合一个算子就省一趟 16MB 读写（≈30 µs@1.06 TB/s）；
2. **低精度**：exp 受限的模板用 fp16/bf16（silu fp16 实测 63.9 µs，1.08–1.13×）；
3. **matmul epilogue 融合**：已实现，历史 1.23–3.38×。

### 方案 E：后端 bug 修复（不涉及 TLE，且我们能重建）

| 目标 | 现状 | 预期 |
|---|---|---|
| **在线 softmax 的 `uni_sram` 误报** | 32×64 tile 都编不过 | 修好后 softmax 可从 native 462 µs 降到 ~150 µs |
| `tl.math.exp2` 结果错误（issue #1） | max_err 1e3 | 修好后可直接用 exp2 构造快速 sigmoid |
| sigmoid 融合缺陷（issue #2） | 已修复并验证 | 为后续硬件数学打通路径 |

### 结论

不依赖 TLE 时，**exp 算力本身没有可行的高速替代**（A/B/C 三条都实测失败）；
能继续做的只有「减少访存趟数的链式融合」「低精度」以及「后端 bug 修复」。
其中 **softmax 的 uni_sram 误报**是收益最大且完全在我们控制范围内的一项（462 → ~150 µs）。


## 四十三、路径三实施：后端 bug 修复（2026-11-06 21:10）

### ✅ 修复 1：`tl.math.exp2` 结果错误（已修复并部署验证）

- **根因**（在 `LegalizeExternEW.cpp` 的注释里被明确写出）：XPU ISA 的 `exp.f.rn` 是**自然指数 e^x**，
  后端把 `math.exp` 映射到 `LLVM::Exp2Op`（其 lowering 就是 `exp.f.rn`）；
  而 `math.exp2` 没有独立 lowering，也落到同一条指令，于是返回 e^x 而不是 2^x。
- **修复**：在 `LegalizeExternEW` 里新增 greedy rewrite `exp2(x) -> exp(x * ln2)`
  （该 pass 在 `convert_triton_to_triton_xpu` 之前运行，覆盖非 SDNN 路径）。
- **验证**（2048² fp32）：`tl.math.exp2` 的 max_err 从 **1665 → 1.5e-5**；
  `tl.exp` 与 sigmoid 仍正确（err 0.0）；exp2 耗时 70.9 µs（与 exp 同级）。
- 源码改动在 `third_party/xpu/lib/Dialect/TritonXPU/Transforms/LegalizeExternEW.cpp`，libtriton 已重建部署。

### ✅ 诊断 2：在线 softmax 的 "uni_sram" 其实是编码不匹配（已定位，附 DSL 规避）

- **真实错误**（被 `compiler.py` 包装层掩盖成 `OutOfResources: uni_sram`）：
  ```
  'arith.subf' op requires the same encoding for all operands and results
      s = s * tl.exp(m - m_new) + ...
  ```
  即循环携带的 1D 累加器 `tl.zeros([R])` 与 reduction 结果 `tl.max(v, 1)` 被分配了不同的
  ClusterLayout 编码（cpg=[1] vs cpg=[g]）。
- **第二个问题**：`compiler.py:620-626` 把 `make_ttxir` 期间任何异常都包成
  `OutOfResources("uni_sram ...")`，把大量非资源 bug 误报为"显存不足"。
- **DSL 规避（已验证）**：累加器改 2D + `keep_dims=True` → 能编译、数值正确
  （err 1.5e-8），2048² 用时 669 µs，仍慢于 native 462 µs，所以**暂不接入产物**，
  但证明了根因是布局而非显存。
- 真正的性能修复需要后端给 scf.for 携带值插入 convert_layout（或从 yielded 值反向传播布局）。

## 四十五、B1 实施进展：打开 IR dump，定位到真正瓶颈（2026-11-06 22:30）

为推进 B1（tile 级 LM staging），先把后端 IR dump 打开（`TRITON_CONCEAL_IR` 改为可选，
新增 `-DTRITON_XPU_CONCEAL_IR_OFF=ON`，重建后 `.ttxir/.llir` 正常落盘），拿到真实 IR。

### 实测 TTXIR（`tl.sigmoid`，2048² fp32）

```mlir
%v_1 = "triton_xpu.alloca"() <{size = 8192}>        // LM 缓冲 8192 元素
%v_5 = "triton_xpu.gm2lm"(%v_4, %v_1) <{syncMode=2}> // ★ GM->LM DMA 已经在做
llvm_xpu.mfence
%v_6 = "triton_xpu.load"(%v_5)                       // LM -> 向量寄存器
%16  = "triton_xpu.svsubf"(%cst, %v_6)               // -x
%17  = triton_xpu.vsigmoidf %16                      // 融合生效（我们的修复）
"triton_xpu.store"(%v_1, %17)                        // VR -> GM
```

### 结论（修正了 B1 的原始假设）

1. **非 TLE 路径已经有缓冲化搬运**（gm2lm DMA 到 LM），"GM→VR"不是瓶颈；
2. **真正的浪费是数学回到向量寄存器**：`triton_xpu.load` 把 LM 数据搬进 VR，
   `vsigmoidf` 的 lowering 又对每个 16 lane 调一次 libdevice（内部 alloca+vstore+mfence+16×exp+vload），
   等于在已经在 LM 的数据上**再做一遍 VR↔LM 往返**；
3. 所以 B1 的正确形态不是"加 staging"，而是**把数学折叠进 LM 常驻循环**：
   `load(LM) → unary 链 → store(GM)` 改写成对 LM 缓冲的标量循环（`loadli.w → exp.f.rn → …`）。

### B1 收敛后的计划

| 步骤 | 内容 | 工期 |
|---|---|---|
| 1 | 新 peephole pass `TritonXPUFoldMathIntoLM`（匹配 LM load → unary 链 → store） | 1 天 |
| 2 | 改写为 LM 缓冲上的 `scf.for` 标量数学循环，入口/出口各一次 mfence | 1 天 |
| 3 | 插入 non-SDNN 管线（gm2lm 之后），用 IR dump 验证没有逐 lane 往返 | 0.5 天 |

预期：Add+SiLU fp32 2048² 78.1 → ~50 µs（1.45×）；sigmoid 76.5 → ~49 µs；softmax 同步受益。
前置条件（IR dump、构建链、硬件 exp 精度、gm2lm/alloca 基础设施）已全部就绪。

## 四十九、Mul+Sum 为什么看起来"全部更慢"——逐条定位（2026-11-07 06:30）

复核最新总表后，"Mul+Sum 全部更慢"并不准确：**FP32 大尺寸其实是赢的**（2048² 1.07–1.09×）。
真正慢的是两类，原因完全不同：

### 1. 小尺寸（两种 dtype）：发射延迟受限

| 项 | 实测 |
|---|---:|
| eager 单算子底噪 | **9.4 µs** |
| Triton 空 kernel 启动 | **12.6 µs** |
| eager `mul+sum`（2 个算子） | 20.7 µs |
| 我们（1 个融合 kernel + 包装） | 22.3–23.7 µs |

64×1024 只有 256KB，真实计算 <1 µs，全部时间都是发射与包装开销：
eager 2×9.4≈18.8 µs，我们 12.6 µs 启动 + Python 包装（region 匹配、shape 校验、
`torch.empty` 分配）≈2–3 µs → 净亏 2–3 µs（0.88–0.90×）。

### 2. 全部 FP16 尺寸 ≥512×1024：快速 DSA 路由在 f16 上完全失效

在 dsa tile 搜索上开了 `FLAGTREE_DSA_DEBUG=1`，2048×2048 fp16 的失败分类：

| 次数 | 异常 | 根因 |
|---:|---|---|
| 6 | `CompilationError at 22:19` | `_packed_kernel` 分配 **int32** DSA buffer，后端只支持 f32/int16 buffer → 每个 tile 都被拒 |
| 12 | `IndexError: tuple index out of range` | 拆分路由（`*_at_1`）用 kind='ew' 调 `_measure_ew`，但只传了 1 个张量（`tensors[1]` 越界） |

把 f16 的非 plain 路径改用通用 `_kernel()` 后，又变成
`TypeError: dynamic_func() missing 1 required positional argument`（measure 调用与 kernel 签名不匹配）。
即 **f16 reduce 的 DSA 路由是死代码**，三种实现各自都坏。

结果：fp16 mul_sum 只能回退 Inductor：

| 形状 | eager | 我们（Inductor 回退） | 相对 |
|---|---:|---:|---:|
| 512×1024 | 20.7 | 45.4 | 0.46× |
| 2048×2048 | 23.8 | 169.8 | 0.14× |

而 FP32 走 DSA 路由：2048² = 31.7 µs（1.07×）。**差距完全来自 f16 路由不可用。**

### 3. 另外：所有 `*_at_1` 拆分路由每次调用都报错

`cluster_sdnn_at_1` / `sdnn_cluster_at_1` 对每个用例都抛
`no correct tile for {'kind': 'ew', ...}`，属于已废弃但未清理的路由，需要在 dispatch 里移除。

### 修复清单（按收益）

1. **修 f16 DSA 路由**（预计 fp16 2048² 170 → 30–40 µs，4–5×）：把 `_packed_kernel` 的
   buffer 改为 `int16`（后端支持），并修正 measure 与 kernel 的调用签名；
2. **移除废弃拆分路由**（消除每次调用的异常噪声）；
3. **压小尺寸包装开销**（目标 22.3 → 20 µs 附近，约 1.0×）：缓存输出分配、减少 Python 侧分支。


## 五十、fp16 Mul+Sum 根因：f16 访存只有 f32 的一半带宽（2026-11-07 08:00）

按上节修复清单动手后，逐步定位到真正的根因，**不是我们 kernel 逻辑错，而是后端 f16 访存路径**。

### 修复的 Python 级 bug（已完成，已部署）

1. `_measure_ew` 增加 `len(tensors) < 2` 保护（消除废弃拆分路由的 IndexError 噪声）；
2. `_plain_round` 增加 `FLAGTREE_DSA_PLAIN_ROUND` 开关（便于实验）；
3. 确认 `_is_plain` 对非 f32 一律走 plain 内核是既有设计（注释也说明 packed-DMA 路径更慢），
   因此之前的 f16 dsa 修复方向不成立，相关试验改动已回退。

### 决定性测量

| 测试（2048²） | 耗时 | 有效带宽 |
|---|---:|---:|
| f32 copy（32MB 流量） | 61.7 µs | **1.09 TB/s** |
| **f16 copy（16MB 流量）** | 56.4 µs | **0.59 TB/s** |
| i32 copy（同 f32） | 61.5 µs | 1.09 TB/s |
| f16 load→f32 store | 31.9 µs | 0.75 TB/s |
| f16 载入+转换+写回 f16 | 32.1 µs | — |
| **eager f16 逐元素（a*2）** | 15.2 µs | **1.05 TB/s** |

结论：
- **Triton 的 f16 load/store 只有 f32 的一半带宽**（0.53–0.59 vs 1.09 TB/s），
  而厂商 eager 的 f16 逐元素能到 1.05 TB/s —— 说明**后端没有把 f16 访存加宽**（官方问题）；
- f16→f32 转换本身不慢（31.9 vs 30.2 µs，几乎无差别），排除我之前怀疑的"转换标量化"；
- 我们的 fp16 mul_sum 内核 121 µs 对应 0.066 TB/s，比 f16 copy 路径（0.53）还差 8×，
  说明 2D 行块 + 大累加器结构在 f16 上效率更低（但即使优化到 copy 水平也只到 ~30 µs）。

### 结论与建议

- **fp16 Mul+Sum 在 Triton 侧无法追平 eager**：根因是后端 f16 访存未加宽（0.59 vs 厂商 1.05 TB/s）；
- 已作为 issue 12 记录（f16 load/store 位宽减半），需要厂商在后端修；
- 我们侧已完成的修复（见上）只消除异常噪声，不改变性能；
- fp32 继续走 dsa 路由（2048² = 31.7 µs，1.07×），这是当前最优。


## 五十一、路径 B 取消："f16 带宽减半"是尾效应假象（2026-11-07 09:40）

原计划做后端补丁（路径 B）让 f16 访存按 32-bit 字打包。动工前用 BLK（程序数）扫描复测，
**结论被推翻，补丁不需要做**。

### 决定性数据（同一份 16MB 数据）

| 配置 | 程序数 | 耗时 | 带宽 |
|---|---:|---:|---:|
| f16 copy BLK=8192 | 1024 | 56.7 µs | 0.59 TB/s |
| **f16 copy BLK=16384** | **512** | **32.3 µs** | **1.04 TB/s** |
| f32 copy BLK=8192 | 512 | 32.4 µs | 1.04 TB/s |
| i32 copy（同字节） | 512 | 32.0 µs | 1.05 TB/s |

**f16 与 f32 在程序数 ≤ ~512 时带宽完全相同（1.04 TB/s）。**
之前的 0.59 TB/s 是因为 BLK=8192 让 8M 元素的 f16 张量产生了 **1024 个程序**
（超过 768 核，形成 1.76× 的尾效应），而 f32 同样 BLK 只有 512 个程序。

### 修正后的结论

1. **后端不需要改**：vectorizer 的 `vecWidth=32`（64B）决策正确，f16 访存没有"未加宽"问题；
2. **真正的问题是分块/程序数选择**（在我们自己的 kernel 配置里）；
3. fp16 Mul+Sum 大尺寸慢（121 µs）与访存无关——它 grid=128 程序（不算多），
   瓶颈在 reduce 内核内层循环（有效 0.066 TB/s，比 copy 低 15 倍），需要单独重构；
4. issue 12 已撤回并记录更正，避免后续误判。

### 下一步

- 用"程序数 ≤ 512"约束重调所有 f16 模板的分块（尤其 flat/plain 内核的 BLK 与 tile）；
- 重构 f16 reduce 内核的内层循环（当前 0.066 TB/s 是主要问题）。


## 五十二、f16 reduce 内核重构尝试（2026-11-07 10:20）

按"减少 VRF 占用"的思路试了新内核结构：每个 chunk 立即 `tl.sum(p, 1)` 累加到 `[ROWS]` 一维向量
（原内核是 `[ROWS, COLS]` 二维累加器，16KB 常驻寄存器）。

结果：

| 配置 | 结果 |
|---|---|
| R4/R8/R16 × C256/C512 | **全部 `OutOfResources: uni_sram`**（实为循环携带 1D 累加器的编码不匹配，即 B2 那个问题） |
| R4 × C1024（f16 512×1024） | 39.3 µs（比现有 28.4 µs 更慢） |
| f16 2048×2048 | 编译失败 |

结论：**这条路被 B2（`scf.for` 携带值的 layout 问题）挡住**——只要把归约中间结果作为
循环携带值，就会触发编码不匹配；而绕开它（保持二维累加器）又会造成 VRF 溢出。
两者互相矛盾，说明 **f16 reduce 的真正修复依赖 B2 的后端 layout 修复**。

### f16 相关修复的最终结论

1. 路径 B（后端 f16 访存打包）**不需要做**——带宽问题已证明是程序数/尾效应假象；
2. f16 Mul+Sum 慢（121 µs vs eager 23.3）的根因是 **reduce 内核结构 + B2 layout 限制**；
3. 可行的低风险止损：**fp16 reduce 直接回退 eager**（当前 fp16 reduce 在所有尺寸都 ≤0.94×，
   回退后全部 ≥1.0×）；
4. 根治顺序：先修 B2（scf.for 携带值 layout），再造 f16 reduce 内核（一维累加器结构）。

## 五十六、三个短板是否“没按推荐写法”：对照官方文档逐条核对（2026-11-07 19:45）

### 官方文档给出的推荐写法（三处来源）

1. `how_to_write_reduce/references/reduce_envelope.md`：
   - 归约轴只能是最后一轴；中间轴必须两趟；
   - 折叠只能 "elementwise adds only"（每列一个累加器 + 逐元素加），循环内不得做归约；
   - 尾块用 `sizes` 不要 mask；tile 形状只能实测；grid "一个 cluster 一个 program 最好"；
   - f16 在 LM/TLE 路径**已知编译受限**（每个 tile 都失败，local-memory budget）。
2. `how_to_write_norm/README.md`：
   - 「统计量的写回就是这个算子」——窄 strip 写回可能比整个 tile 流量还贵（30us kernel 里 +19.3us）；
   - 根因是 8 个 cluster 撞同一条 64B cache line；解法是走 **cluster 共享 SM**（`scope=tle.gpu.smem`）；
   - bf16/f16 上不了这条路，只能 gate 回 LM。
3. `XTDK 用户手册 §3.1.2.4`（厂商手写 kernel 范式）：
   - 1-D 连续分块、按 `cluster_id/core_id` 均分、`align=16`；
   - **每核 LM 缓冲 `buf_len = 1536`**（`__simd__ float local[1536]`），GM2LM→cast→`primitive_exp`→cast→LM2GM。

### 逐模板判定

| 短板 | 是否“没按推荐写法” | 依据与现状 |
|---|---|---|
| **Softmax 2048²**（407 µs，0.182×） | **部分是**（且本轮已修一个真问题） | 我们之前**根本没选中自己的 kernel**（tile 搜索全部判失败 → 回退 Inductor 848 µs）。重新部署后选中 `r16 c256 warps4`，**407 µs = 比 Inductor 快 2.08×**，但仍慢于 eager（74 µs）。剩余差距来自：① 文档推荐的两趟 online 形式被 B2（循环携带 layout）挡住，我们只能三趟；② 我们的 exp 比厂商 `primitive_exp` 慢 ~2.7× |
| **LayerNorm 2048²**（214 µs，0.232×） | **部分是** | 结构符合文档（每列累加器 + 逐元素折叠 + 循环后归约），但两个 `[R,C]` f32 累加器（32KB）造成 VRF 压力；文档推荐的"统计量写回走 cluster 共享 SM"只存在于 TLE 路径，我们是 plain 路径用不上；厂商范式是每核 6KB LM 缓冲（1536 元素）而不是 32KB 寄存器累加器 |
| **fp16 Mul+Sum 2048²**（117 µs，0.198×） | **基本不是** | 文档明确写了 f16 在 LM/TLE 归约路径的编译限制，官方建议就是回退；plain 路径的性能是 Triton codegen 限制（f16 表达式树/转换），不是写法违规 |

### 结论

- 三个短板里，**softmax 的问题是"路由/瓦片选择"（我们自己的代码）**，本轮已修：0.087 → **0.182×**（相对 Inductor 2.08×）；
- **layernorm 的问题是"累加器放寄存器还是 LM"（写法 + 后端能力）**，按厂商范式重写需要 TLE/descriptor 路径，且 f16/bf16 在该路径本身受限；
- **fp16 mul_sum 是官方文档明示的限制**，不是写法问题。

### 下一步可做（按性价比）

1. 把 reduce 内核改成**厂商范式**：每核 1-D 连续分块 + 小 LM 缓冲（1024/1536 元素）+ 逐块 `sum` 折叠，替代 `[R,C]` 寄存器累加器——预计能同时改善 layernorm 2048² 与 fp16 mul_sum；
2. softmax 走两趟 online 需要先修 B2（官方）。


## 五十七、按厂商范式重写 reduce 内核：试过，行不通（2026-11-07 19:55）

按 XTDK 手册 §3.1.2.4 的范式实现了一版新 reduce 内核：每程序处理 ROWS 行，
**每行一个 1-D 累加器（长度 C=256..2048，4·C 字节常驻）**，按块逐元素折叠，
循环结束后再 `tl.sum` 归约（`static_range` 展开行循环）。实测对比：

### 现状与选项

1. 继续在更晚的 pass（Legalize / Vectorize / 内联之后）挂协调逻辑——每轮约 5 分钟重建，属于试错；
2. 或者在**前端/内联层**处理：让这些 `triton.language.standard.*` helper 在 TTIR 阶段完成内联
   （正常内核里它们本来会被内联，online 结构下没有）；
3. **保留现状**：softmax 三趟 409 µs（相对 Inductor 2.08×），不阻塞其它模板。

> 结论：B2 的"布局协调"组件已经写好并通过回归，但 online softmax 还卡在 helper 内联/编码路径上，
> 尚未拿到最终收益（409 → ~200 µs）。


## 五十九、B2 继续深入：又暴露两层后端问题（2026-11-07 20:35）

在五十八节的基础上，把协调逻辑扩展并挂到更多 pass：

| 扩展 | 结果 |
|---|---|
| `requiresSameEncoding` 加入 `cmpf/cmpi/andi/ori` | 重编译通过 |
| 在 `Vectorize` 末尾也挂 `reconcileClusterLayouts` | 重编译通过 |
| 回归（mul_sum/silu/layernorm/softmax 512×1024） | 与基线一致，无副作用 |

但 online 形式仍编译失败，且失败点随写法变化：

| 写法 | 失败点 |
|---|---|
| `tl.max` + `tl.maximum`（原版） | `'arith.maxnumf' op requires the same encoding` |
| `tl.reduce(..., max_combine)` + `tl.where(m > cm, ...)` | `'arith.cmpf' op failed to verify that result type has i1 element type and same shape as operands` |

第二个错误是 **Vectorize 的重类型化问题**：`cmpf` 的两个 f32 操作数被重类型化成
`vector<16xf32>`，但 i1 结果仍是 `tensor<...xi1>`（或形状未跟随），与"循环携带值编码"
是两件事。也就是说 **online softmax 在本后端至少叠加了 3 层问题**：

1. 循环携带值 vs 归约结果的编码（我们已写协调逻辑）；
2. `tl.max/tl.sum` 标准库 helper 的 `tt.call` 内联路径；
3. `Vectorize` 对 `cmpf/select` 的重类型化不完整。

### 结论

- B2 的布局协调组件已经落地、可编译、回归无副作用，但**单独修它不足以打通 online softmax**；
- 继续做下去需要动 `Vectorize` 的重类型化逻辑，属于更深的编译器改造（风险与工作量都上一个台阶）；
- 当前 softmax 仍用三趟：409 µs（2048²），相对 Inductor **2.08×**；
- 建议把"B2 + helper 内联 + cmpf 重类型化"作为一组后端 issue 提交，同时保留我们的协调 pass 作为前置补丁。

# 二、本周修复的 issue

> 格式参照 [FlagTree#1458](https://github.com/flagos-ai/FlagTree/issues/1458)：`问题 / 复现 / 修复与验证`。
> 按「正确性 → 可诊断性 → 工程构建 → 性能与路由」分组。

## A. 正确性

### A1. `[XPU] tl.math.exp2 computes e^x instead of 2^x` — 已修

**问题**：`tl.math.exp2` 下发到 `llvm.xpu.exp2f`，该 intrinsic 在硬件上对应 `exp.f.rn`（自然指数），无除法修正。入口 `Transforms/LegalizeExternEW.cpp`。

**复现**：`tl.math.exp2` 内核 vs `torch.exp2`，`x~N(0,1)`、65536 元素：修复前 `max_err ≈ 1665`。

**修复与验证**：新增 `Exp2ToExpScaledPattern`，改写为 `exp(x*ln2)`。验证 `max_err = 0.0`。

### A2. `[XPU] sigmoid fusion never fires` — 已修

**问题**：`Transforms/Vectorize.cpp` 两处缺陷：① 融合条件用**操作对象指针**比较而非操作数值；② `Div2Mul` 重写在融合**之前**执行，提前改写掉 `div`。

**复现**：编译 `y = x/(1+exp(-x))`，`Vectorize` 后 IR 中搜不到融合产物。

**修复与验证**：改为 `isSplatOne(...)` 值判断；`Div2Mul` 移到融合之后；放宽 exp 输入检查（接受零 splat LHS 的 `VvsubFOp`）。验证融合触发，模板无退化。

### A3. `[XPU] B2 — loop-carried tensor encoding mismatch on the plain path` — **部分修复**

**问题（B2 定义）**：plain 路径下 `scf.for` 携带值（iter_arg）保持类型转换器的默认 ClusterLayout，而循环内归约结果（`tl.max/tl.sum` 的输出）是 slice 编码；后端未在两者之间插入 `triton_xpu.convert_layout`，`arith` 校验直接失败：
`'arith.subf'/'arith.maxnumf' op requires the same encoding for all operands and results`。
入口 `Conversion/TritonToTritonXPU/TritonToTritonXPUPass.cpp`（`SCFForPattern` + 类型转换器）；
TLE 路径在 `TLECoreTiling.cpp:198-210` 已修补（`getCluster1DForSliceDim` 强制 `cpg=[g]`），**plain 路径没有等价逻辑**。修复前该错误还被 `compiler.py` 包装成 `OutOfResources: uni_sram`（见 B1）。

**复现**：循环携带 1D 累加器 + 循环内归约的 online softmax；**官方 wheel 原库同样报错**，与本仓库改动无关。

**修复与验证**：新增 pass `tritonxpu-reconcile-layouts`（`Transforms/ReconcileLayouts.cpp` + `ReconcileLayoutUtils.h`），在转换 / `Normalize` / `Vectorize` 三处挂钩，为 `scf.yield`→iter_arg 及要求同编码的 elementwise op（含 `cmpf/select`）插入 `convert_layout`。验证：编译通过，4 模板回归**零副作用**；online softmax 未打通（见 U1）。

## B. 可诊断性

### B1. `[XPU] make_ttxir masks every failure as OutOfResources("uni_sram")` — 已修

**问题**：`backend/compiler.py` 把 `make_ttxir` 阶段所有异常包成 `OutOfResources(0,0,f"uni_sram {e}")`，布局/校验错误被伪装成显存不足。

**复现**：online softmax 内核：修复前报 `uni_sram`，真实错误是 `'arith.subf' requires the same encoding…`。

**修复与验证**：仅当异常是 `OutOfResources` 或消息含真实资源标志（`Buffer alloc failed` / `out of resource` / `SRAM` / `local-memory budget`）时包装，其余原样抛出。验证：报错恢复为真实编码错误。

## C. 工程与构建

### C1. `[XPU] build fails with -Werror on LLVM 22; IR dump hard-disabled` — 已修

**问题**：`cmake/FlagTreeOptions.cmake`、`CMakeLists.txt` 无条件 `-Werror`（LLVM 22 deprecated 警告直接失败）；`TRITON_CONCEAL_IR=1` 硬编码使 IR dump 无效。

**复现**：按官方配置 + LLVM 22.1.8 构建直接失败；`TRITON_KERNEL_DUMP=1` 输出为空。

**修复与验证**：移除 `-Werror`；新增 `TRITON_XPU_CONCEAL_IR_OFF` 选项。验证：构建通过、可 dump `.ttxir/.llir`（B2 定位即依赖它）。

## D. 性能与路由（我方代码）

### D1. `[XPU] graph-fusion kernels re-specialise on every call` — 已修

**问题**：`_p800_flat.py` / `_p800_reduce.py` 指针进 specialization key，违反官方「指针别进 key，否则每次调用重新加载 kernel（10–30 ms/次）」。

**复现**：同内核连续调用 `first ≈ median` 且偏高；指针 divisibility 变化即触发重载。

**修复与验证**：kernel 加 `do_not_specialize=[所有指针]`；reduce 改为首次调用绑定 launcher（官方建议「绑定一次省 ~9 µs」）。验证：Add+SiLU 1.10→**1.14×**，Add+LayerNorm **1.11–1.13×**。

### D2. `[XPU] Add+Softmax 2048² silently falls back to Inductor` — 已修

**问题**：`_p800_reduce.py` tile 搜索对该用例所有候选判失败 → 回退 Inductor（846.7 µs），而同一内核独立基准可达 409 µs。

**复现**：`eager_table.py add_softmax 2048x2048 float32` → `{"route":"inductor","us":846.7,"vs_eager":0.087}`。

**修复与验证**：重部署覆盖层并清 tile 缓存后选中 `r=16,c=256,warps=4`。验证：`408.4 µs, vs_eager=0.180`，**相对 Inductor 2.08×**，err 1.7e-10。

## E2　rank-1 wrap pass 把合法的 modulo load 当致命错误（已修复）

- **问题**：`Rank1Wrap.cpp` 的 `CaptureRank1Wrap`（#1458 修复引入）要求 rank-1 modulo load 必须匹配
  `arg + (pid*BLOCK+lane) % PERIOD` 且带 `x < LENGTH` 的 `arith.cmpi slt` mask；不匹配即 `signalPassFailure()`。
  Inductor 为激活段生成的广播 load（`x0 = xindex % 2048; load(ptr + x0)`）**没有 mask**，
  于是所有经过 SDNN 激活段的 MatMul+Activation 区域编译失败（表现为 `error 702` / 编译错误）。
- **修复**：不匹配的 load 改为**跳过**（保留匹配模式的 wrap 修复，并以 `emitRemark` 记录跳过数量），不再让 pipeline 终止；
  重建后 `libtriton.so` md5 `4d51b3f34f57`。
- **效果**（fp32，空闲卡，修复 + 策略）：

| 用例 | 修复前 | 修复后 |
|---|---|---|
| matmul_bias_gelu_exact 64/512/2048 | 1.00 / 1.04 / 1.47 | **1.22 / 1.54 / 3.12×** |
| matmul_bias_gelu_tanh | 编译失败 | 编译通过但慢 4–25× → 策略 decline，1.00–1.82× |
| matmul_bias_silu | 512/2048 `error 702` | 编译通过但慢 1.4–25× → decline，1.00× |
| **fp16** matmul_bias_gelu_exact 64/512/2048 | 1.00 / 1.16 / 1.31 | **1.28 / 1.62 / 3.06×** |

# 五、修不了的 issue：为什么它们导致我们比 eager 慢

> **共同机理**：eager 用的是厂商手写 C++ kernel——**单趟 online、1536 元素 SIMD 批量 exp、f16 原生处理、
> 每核 6 KB LM 常驻缓冲**。我们在 plain Triton 路径上这四项能力都缺，只能退化成
> **多趟遍历 / 标量 exp / 逐元素 f16 转换 / 32 KB 寄存器累加器**，
> 每一项都直接放大访存或计算量，因此大尺寸被 eager 反超。以下逐条给出"机理 → 数值"。

### U1. B2 第 2/3 层：helper 内联 + `cmpf/select` 重类型化

- **定位**：前端把 `tl.max/tl.sum` 保留为 `tt.call @triton.language.standard.*`；内联后 `arith.maxnumf` 的操作数编码分属"调用结果"与"归约结果"；换成 `tl.reduce + tl.where` 后，`Vectorize` 把 f32 操作数改成 `vector<16xf32>` 而 i1 结果未同步。
- **为什么修不了**：需改 `Vectorize` 重类型化分支，属编译器中段改造；协调 pass 已挂转换/`Normalize`/`Vectorize` 三处，错误仍在其后触发。
- **为什么导致比 eager 慢**：eager 的 softmax kernel 是**单趟 online**（寄存器里维护 running max/sum），只读一遍数据；我们写不出 online（编译失败），只能**三趟**——max、sum、normalize，数据读 3 遍、写 1 遍，2048² 即 64 MB 流量（eager 32 MB），且 exp 要算两次而不是一次。
- **量化**：2048² **408.4 vs 73.4 µs（0.18）**、512×1024 55.5 vs 20.7（0.37）；打通后目标 ~200 µs。

### U2. 设备端没有向量 exp

- **定位**：`libdevice-xpu3.bc` 只有标量 `xpu::expf(float/half)`；向量只有 `vsigmoidf/verf/vtanhf`；硬件 `exp.f.rn` 为标量指令。
- **为什么修不了**：没有标量 LM 访问 intrinsic，无法安全实现"1536 元素批量 staging"；5 种尝试（寄存器版 89.7 µs、inline asm 80.9 µs、alloca 崩溃 719、批量 asm 超时 299、厂商 IR hang 卡）全部失败。
- **为什么导致比 eager 慢**：厂商 `primitive_exp` 一次处理 1536 元素缓冲，**mfence 少 96 倍**；我们的 exp 每 16 lane 一次 LM 往返 → 16MB 一次全量 exp 要 44 µs，厂商只需 16 µs。SiLU/GELU/Softmax 大尺寸本质是 exp 受限，所以我们的计算时间被放大 2.7×。
- **量化**：Add+SiLU 2048² **78.3 vs 72.0 µs（0.92）**；Softmax 的 408 µs 里两次全量 exp 约占 90 µs。

### U3. f16 在 LM/TLE 归约路径不可用

- **定位**：官方 `reduce_envelope.md` 明示 f16 归约在 LM/TLE 路径每个 tile 都编译失败（local-memory budget）；f16 packed DSA 路径因 int32 DSA buffer 被后端拒绝。
- **为什么修不了**：需后端支持 f16 归约（或放宽 DSA buffer dtype），属官方改动。
- **为什么导致比 eager 慢**：eager 的 f16 reduce 是厂商原生 kernel——f16 载入后**向量化转换**（`vhalf2float_l/h_rn`）、单趟归约、每核小缓冲；我们只能走 plain 路径：每个元素做一次 f16→f32 转换 + 2D 累加器，有效带宽掉到 **0.066 TB/s**（纯 f16 流式拷贝可达 1.04），等于把 8 MB 数据当 120 MB 处理。
- **量化**：fp16 Mul+Sum 2048² **118.5 vs 23.6 µs（0.20）**；fp16 LayerNorm 2048² 0.12。

### U4. LayerNorm 大尺寸的累加器无处安放

- **定位**：`_p800_reduce.py` 用两个 `[R,C]` f32 累加器（sum、sumsq），4096 元素时共 32 KB，超出 VRF。
- **为什么修不了**：plain 路径没有 LM 常驻累加器；厂商范式需要 `primitive_*` + LM 缓冲，在 Triton 里重写后反而慢 3.3×（已回退）。
- **为什么导致比 eager 慢**：累加器溢出到 LM 后**每次循环迭代都要 spill/reload 32 KB**；厂商 layernorm 每核只用 6 KB LM 缓冲逐块折叠，几乎不溢出。两趟带宽下界只有 44 µs，我们实测 215.8 µs，多出的 ~170 µs 基本就是 spill 成本。
- **量化**：LayerNorm 2048² **215.8 vs 49.6 µs（0.23）**、fp16 272.0 vs 31.6（0.12）。

### U5. `tle.dsa.local_ptr` 在 XPU 缺失

- **定位**：`tle_cn.md` 3.3.2.1.3 有描述，只有 Ascend 实现；XPU 的 `tle.dsa` 仅有 `alloc/copy/to_tensor`。
- **为什么修不了**：需厂商补 lowering，或提供 batched vector-math 入口（如 `vsigmoidf_n(ptr, n)`）。
- **为什么导致比 eager 慢**：它是 U2 的**唯一绕行方案**——若能把 exp 做成"LM 批量缓冲 + 一次 mfence"，就能追上厂商的 16 µs；原语缺失使批量数学无法实现，只能继续用逐 16 lane 的标量 exp。
- **量化**：间接体现在所有 exp 模板（Add+SiLU 2048² 0.92、Softmax 0.37/0.18）。

### U6. SDNN 预编译对象缺陷（拆成三条）

- **U6a rank-1 取模丢失**（[FlagTree#1458](https://github.com/flagos-ai/FlagTree/issues/1458)）：
  修复位于分支 `origin/codex/p800-sdnn-modulo`（commit `2364b8c54`），**未合入 main**；
  我们已 cherry-pick、重建库、并在已安装 `compiler.py` 补两个管线钩子。
  **验证**：官方复现脚本 period 7/17/32 全部 `gate_passed=True`、错误项 0。✅ 已解
- **U6b `sdnn.core_specialize` 编码不匹配**：报错为 region 参数 `tensor<16xf32>` 与操作数
  `tensor<16xf32, #sdnn.rc<layout="RC", blockColHeight=16>>` 不一致。**属于写法问题**：
  用一维累加器写归约时拿不到 RC 编码；改成官方文档推荐的 **2D `keep_dims` 累加器 +
  elementwise 折叠** 后即可编译（不再报该错）。✅ 写法已规避（文档未专门写 SDNN 编码，
  依据的是 `reduce_envelope.md` 的通用规则：归约轴在最后、只做逐元素折叠、二维累加器）
- **U6c SDNN 归约数值错误**：即使按上述写法编译通过，SDNN layernorm 结果仍错
  （实测 `max_err` 50–82，2048² 为 82.4），与 modulo 无关（layernorm 不含取模）。
  源码不可见（`libTritonSharedForXPU.a` 预编译），只能等厂商修。❌ 未解
- **为什么不再追 SDNN**：即便数值正确，SDNN 这条 reduce 形状并不快——
  layernorm 2048² SDNN 实测 **390.6 µs**，而 cluster 路由 **215.8 µs**；
  SDNN 只在 `mul_sum 2048²` 与 cluster 持平（31.8 µs）。因此 reduce 类模板继续走 cluster。


### U7. MatMul 模板不可测（环境问题；SDNN 强项因此缺席）

- **定位**：152 上 **eager matmul 本身**就失败：XBLAS jitc 报
  `Failed to create compile directory under /tmp` → `RuntimeError: error code=15`。
  已尝试 `XBLAS_JITC_CACHE_PATH`、`XBLAS_JITC_CACHE_ENABLE`、`XMLIR_DISK_CACHE_DIR`、`TMPDIR`
  均未绕过（`/tmp` 可写、剩余 16 GB，问题在 jitc 的目录创建逻辑）。
- **为什么修不了**：XBLAS 运行时环境问题，非代码；需要环境维护方处理。
- **为什么与 SDNN 有关**：官方 `launch_configuration.md` 明确 SDNN 内核由管线在
  **源码含 `tl.dot`** 时自动选择——**MatMul 家族正是 SDNN 的强项**。我们的 matmul 融合
  正是走 `tl.dot`（`_p800_matmul.py` 在 `metadata.is_sdnn` 为真时 resource 记为 `sdnn`），
  但 152 上连 eager 都跑不起来，因此 **SDNN 强项的加速比本周无法纳入表格**——是"测不了"，
  不是"没用"。
- **量化/后续**：历史（81 卡）MatMul 融合 1.23–3.38×；需在 81 或修复 XBLAS 后补测。

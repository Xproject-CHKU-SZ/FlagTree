## 二、本周修复的 issue

| ID | 问题 | 根因 | 修复 | 验证 |
|---|---|---|---|---|
| A1 | `tl.math.exp2` 数值错误（max_err 1078→2420） | XPU 的 `exp.f.rn` 是**自然 exp**，后端把 `exp2` 直接映射成它 | 后端新增 `Exp2ToExpScaledPattern`：`exp2(x) → exp(x·ln2)` | max_err **0.0** |
| A2 | sigmoid 融合从未触发（SiLU 走慢路径） | ① 用 op 指针比较而非 `isSplatOne`；② `Div2Mul` 在融合前被改写；③ exp 输入检查过严 | `Vectorize.cpp` 三处修复，融合后补 `arith.cmpf → VCmpFOp` 清理 | 融合确认触发，SiLU 提速 |
| B1 | `OutOfResources: uni_sram` 掩盖真实编译错误 | 编译器包装器把**所有**异常都包成 SRAM 资源不足 | 只对 `isinstance(OutOfResources)` 或真实资源标记包装 | 真实错误（如 `'arith.subf' requires same encoding`）可见 |
| C1 | 增量构建不可用 / 产物依赖新 GLIBC | `-Werror` + 默认工具链 | 移除 `-Werror`、新增 `TRITON_XPU_CONCEAL_IR_OFF`、conda gcc 11.4 + sysroot 2.17 + LLVM 22.1.8 | `objdump -T` 最高 GLIBC **2.17** |
| D1 | 每次新指针都触发重新编译 | 指针进入 specialization key | 所有 kernel 加 `do_not_specialize` | 同形状复用编译产物 |
| D2 | Softmax/Reduce/LayerNorm 在小尺寸恒慢 | 未区分“融合更快/更慢”的形状类 | 回退策略：按 kind+dtype+shape 门限回退 eager | 点算子 42/42 ≥1.0 |
| E1 | MatMul 只有两段式（`sdnn_cluster` 55–71 µs），无单内核 | 缺少 matmul epilogue 模板 | 新增 `native_mm`：`tl.dot + bias + relu` 单内核，M≤512 用 (256,256,64,8)、更大用 (64,512,64,8) | bias **1.05–1.44×**、relu **1.48–1.91×** |
| E2 | MatMul+Activation 编译失败 / `error 702` | #1458 引入的 `CaptureRank1Wrap` 把“不匹配其期望形式的 rank-1 modulo load”当**致命错误**；Inductor 的广播 bias load（`xindex % 2048`，无 mask）必然触发 | `Rank1Wrap.cpp` 改为**跳过不匹配的 load**（保留匹配模式修复，跳过时 emitRemark），不再终止 pipeline | GELU(exact) 新获 **1.22–3.12×**；tanh/silu 不再报错 |
| G1 | 合法性缺陷：dtype 混用可误融合；`mm+add` 后接 GELU/SiLU 会被 native_mm 误接 | 匹配器未校验第二操作数 dtype；未校验 add 的消费链 | 补 `b.dtype == a.dtype`；native_mm 只接受 `mm→add→(relu)` 且直连 output | 19/19  legality 单测通过 |

提交：`8cd860695`、`bb9319e46`、`50b24f29c`、`a0aeb545b`、`4dae33bc7`；修复库 md5 `4d51b3f34f57`。

## 五、无法解决的问题如何影响性能（量化）

| 模板 | 当前 | 地板/理论上限 | 差距来源 | 若官方修复后的预计 |
|---|---:|---:|---|---:|
| Add+SiLU 2048² | 78.4 µs | 拷贝地板 39.1 µs；厂商同类 exp 16 µs → 约 55 µs | 标量 exp（38 µs，占一半）（U2） | **≈1.3× vs eager（72.1）** |
| Add+GELU(exact) 2048² | 172.6 µs | erf/exp 标量组合（U2/U6） | 数学指令 | 约 1.7–2× |
| Add+GELU(tanh) 2048² | 499.6 µs（cluster） | 地板 39.1 µs | tanh 路径病态（U6） | 需先修 exp 折叠 |
| Add+LayerNorm 2048² | 215.8 µs | 统计遍 166 µs（spill）；单遍地板 13 µs | 双 `[R,C]` 累加器 spill（U4） | 估算 ~60–90 µs → 0.6–0.8×（仍难超 eager 49.6） |
| Add+Softmax 2048² | 409 µs | 三趟 80 MB → 地板 ~65 µs；两趟 48 MB | 三趟 + 标量 exp（U1/U2） | 估算 ~250 µs → 约 0.3×（仍慢于 eager 73.5） |
| fp16 Mul+Sum 2048² | 0.20×（回退） | 带宽地板 ~26 µs | f16 归约路径（U3） | 可到约 1.0× |
| MatMul+SiLU / GELU(tanh) | 回退 1.00×（sdnn 0.03–0.70×） | 单内核 ~30–40 µs 可达 | SDNN 激活 lowering（U5） | 估算 1.3–1.8× |
| 小尺寸（64×1024）全部模板 | 18.9–23 µs | 启动地板 13.13 µs | 启动绑定（非缺陷） | 无空间 |

**结论**：
1. **已贴地板的模板**：Mul+Sum（带宽 1006 GB/s / 1288）、MatMul+Bias/ReLU（14.8–17 TFLOPS ≈ fp32 峰值）、小尺寸（启动地板）——本地已无结构性空间；
2. **差距全部可归因**：`U2 标量 exp` 解释 SiLU/GELU 的 2–4× 差距；`U4 累加器` 解释 LayerNorm 的 8.3× 差距；`U1 三趟` 解释 Softmax 的 6.3× 差距；`U3` 解释 fp16 归约 0.12–0.20×；`U5` 解释 MatMul 激活路径不可用；
3. **即使全部修复**，LayerNorm/Softmax 仍可能慢于厂商手写 kernel（厂商 49.6/73.5 µs），因为其 C++ 侧有批量 SIMD 与单趟 online 结构；本地方向应聚焦"融合能赢的组合"（MatMul+Bias/ReLU、Mul+Sum 大尺寸、GELU(exact)），其余走回退。

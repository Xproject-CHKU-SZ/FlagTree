## 3. 基线问题表现

验收测试命令如下：

```bash
FLAGTREE_BACKEND=xpu \
CUDA_VISIBLE_DEVICES=0 \
KLX_USE_AUTOTUNE=0 \
XMLIR_MATMUL_FAST_MODE=1 \
PYTHONPATH=/env/FlagGems/src \
python /experiment/legacy_sdnn/run_pytest.py \
  --profile diagnostic \
  --output /experiment/results/baseline-pytest/compiler_copy.py \
  /env/FlagGems/tests/test_blas_ops.py::test_accuracy_mm -q -s
```

基线结果：

```text
6 passed, 12 failed
```

失败日志中的两类错误为：

1. 大形状在 `TritonToLinalgExperimental/StructuredToMemref` 阶段报：
   `expected result type with size = dynamic instead of N`。
2. 小形状 BF16 在 bufferization 阶段报：
   `element types do not match`。

此前的 `(1, 1, 32)` FP16/FP32 还可在 `make_llir` 阶段触发 LLVM `bad signature` abort。诊断 compiler 副本仅用于保留 TTXIR 原始异常和控制早期 combine，不构成这两类后端类型问题的修复。

## 4. 根因定位

FlagGems Kunlunxin `mm_kernel` 原实现使用：

- `tl.arange` 生成二维索引；
- 普通指针加法构造 A/B/C 地址；
- `tl.load`、`tl.store`、`tl.atomic_add` 使用 mask 处理边界；
- M/N/K 为运行时参数。

该表示在 XPU3.6 的 TTXIR 到 Linalg/StructuredToMemref lowering 中暴露了两类问题：

- 普通指针张量的静态 tile 类型与运行时 M/N/K 的动态维度无法满足 StructuredToMemref 的结果类型合同；
- BF16 路径中由 masked pointer load/store 生成的 buffer element type 与后续 bufferization 类型不一致。

诊断 profile 通过 `XPU_SDNN_PRESERVE_TTXIR_ERRORS=1` 保留原始异常，证明原先的 `OutOfResources: uni_sram` 是 compiler 包装后的表象，并非已经测得的 SRAM 容量不足。

## 5. 实际修复

修复文件：

```text
third_party/xpu/compat/legacy_sdnn/04-flaggems-mm-block-pointer.patch
```

补丁对 `src/flag_gems/runtime/backend/_kunlunxin/ops/mm.py` 的 `mm_kernel` 做了以下改变：

1. 使用 `tl.make_block_ptr` 描述 A、B、C 的二维 shape、stride、offset 和 tile shape。
2. 使用 `boundary_check=(0, 1)` 和 `padding_option="zero"` 处理动态边界，去除普通指针 mask load/store 造成的类型歧义。
3. 通过 block pointer 执行 `tl.store` 和 split-K 的 `tl.atomic_add`。
4. 保留原有矩阵乘、累加 dtype、split-K 和输出 dtype 语义，没有引入 native fallback。

配套运行条件：

```bash
export PYTHONPATH=/env/FlagGems/src
export FLAGTREE_BACKEND=xpu
export CUDA_VISIBLE_DEVICES=0
export KLX_USE_AUTOTUNE=0
export XMLIR_MATMUL_FAST_MODE=1
export XPU_SDNN_PRESERVE_TTXIR_ERRORS=1
```

`XMLIR_MATMUL_FAST_MODE=1` 是当前标准镜像中使 BF16 验收路径进入可用 lowering 的必要运行配置，不是跳过测试、排除算子或 CPU fallback。

补丁 SHA256：

```text
6d71234ed81c9da28806ce62a426d34d8307f99069d78785f3f2a89a85b81400
```

扩展补丁：

```text
05-flaggems-bmm-block-pointer.patch
06-flaggems-addmm-composition.patch
```

当前直接 ADDMM 补丁同时完成四项修复：A/B/C 使用 block pointer；bias 以 FP32 传入；输出按 C 指针 element type 转换；兼容模式固定 `32x32x32` tile，避免 XPU3 autotuner 大形状零耗时。

其中 BMM 使用 block pointer，并在 `KLX_USE_AUTOTUNE=0` 下固定一个可复现 tile
配置；ADDMM 使用 FP32 的 FlagGems MM 完成矩阵乘、alpha/beta 和 bias 组合，再转换回
输入 dtype。该 ADDMM 路径仍属于 FlagGems 生态，不调用 CPU/native fallback。

## 7. 变更边界与当前限制

- `03-sdnn-ttxir-diagnostics.patch` 是诊断开关，不是动态形状/BF16 的最终修复。
- `04-flaggems-mm-block-pointer.patch`、`05-flaggems-bmm-block-pointer.patch` 和
  `05-flaggems-addmm-block-pointer.patch` 当前覆盖 FlagGems Kunlunxin `mm/bmm/addmm`
  验收路径，未证明其他 FlagGems 算子均有同类兼容性。
- 旧版直接 ADDMM block-pointer 变体会在 bias load 上触发类型合同错误；当前补丁通过 FP32 bias、输出 dtype 转换和固定 tile 消除该错误。
- 自定义严格 minirepro 使用更严格的 FP64 CPU 参考判据时，补丁可完成 12 组编译，但仍有 6 组数值误差超过该额外判据；这不等同于官方 `pytest18` 验收失败，说明后续需要按项目实际 FP16/BF16/FP32 精度标准单独评估。
- 该补丁依赖当前镜像中的 Triton/FlagTree/FlagGems/SDK 组合。更换 SDK、`libtriton.so`、FlagGems commit 或 tile 配置后必须重新运行基线和验收。
- 当前没有获得 TritonSDNN/StructuredToMemref 的实现源码，因此没有对后端 C++ lowering 做未经证实的修改。

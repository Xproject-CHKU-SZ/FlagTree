一页看懂：本阶段交付了什么

核心变化不是“又支持了一个模型”，而是建立了一条可复用的工程链路：先把不同框架收敛为统一模型图，再用机器可执行的规则确认转换前后的语义没有悄悄改变。

统一 IR 语义规范

解决“图虽然统一了，但算子、dtype、Shape 和 layout 的含义是否一致”。引入版本化注册表、语义契约和逐算子可执行规则。

最重要的管理结论当前已经从“单点脚本验证”推进到“统一产物 + 自动语义检查 + XPU 复验”的可复用链路；下一阶段的重点应从继续堆演示样例，转向 250/500 模型的分层统计、缺口聚类与规则补齐。

Big picture：两个模块怎样首尾衔接

模块一负责“把模型送进来并统一形态”，模块二负责“把统一后的含义说清楚并检查出来”。模块二直接消费模块一生成的 Core ATen 与 manifest，因此两者是前后相接，而不是两套独立工作。

职责边界Core ATen 是模型级统一表示；FlagTree / Triton 仍负责后续 Kernel 级 Lowering、优化和设备代码生成。语义注册或 XPU 跑通，不等于所有算子都已生成 FlagTree 自有 Kernel。

功能模块一：多框架接入与统一 Core ATen

目标是将 PyTorch、ONNX、TensorFlow 的模型结构、类型、Shape 与控制流信息，汇入同一种可保存、可回读、可核对的模型级中间表示。

动态 Shape

把 ONNX 转换图中的 Shape Tensor 改写为 tuple / SymInt 运算；同一 PT2 覆盖多组 batch 与 sequence，不再为每组输入尺寸分别导出。

结构化控制流

ONNX If、Loop、Scan 分别映射到 torch.cond、torch.while_loop 与函数式缓冲区；支持嵌套和真实迭代长度。

可追溯产物

每次导出保存 PT2、manifest、可读图、样例输入和验证报告，确保后续 XPU 复验使用的是同一张图，而不是口头描述。

为什么中型模型此前会卡住

转换器原始表达

Shape(x) → Tensor([B, S]) Gather(shape, 0) → Tensor(B) Concat(...) → Tensor([B,S,H]) Reshape(x, shape_tensor)

FakeTensor 阶段没有真实数据，.item() 或列表化会破坏符号 Shape 传播。

→

本次兼容改写

x.shape → (SymInt B, SymInt S) getitem(shape, 0) → B tuple concat → (B,S,H) reshape(x, symbolic_tuple)

Shape 回到尺寸语义，符号范围随 ExportedProgram 保存并用于多 Shape 运行。

功能模块二：把“图能转换”升级为“语义可证明”

仅仅看到算子名称并不足以证明转换正确。比如同样叫 reshape，是否保持元素总数；同样叫 reduce，dim 与 keepdim 是否正确；同样叫 expand，stride 是否体现广播，这些都需要机器可执行的规则。

注册表

版本 2026.09.22，内容哈希固定；定义算子族、dtype、Shape、layout 和扩展命名空间，便于判断两个产物是否依据同一套规范。

精确参数

operator_instances 保存普通参数和 kwargs，因此检查器能看到真实的 dim、keepdim、permutation、padding 和 slice bounds。

诚实覆盖率

把已执行、失败、尚未实现、元数据不足分开统计。只有真正运行过检查器的规则才进入执行比例，避免用“登记覆盖率”代替完成度。

本轮新增规则覆盖面

类别已经能够执行的代表性检查典型问题
dtype同类型提升、除法浮点路径、累加类型、Where 条件、索引整数、Cast 目标类型、Dropout mask防止静默窄化、错误索引类型和转换目标丢失
Shape符号广播、matmul、transpose、concat/stack、expand/repeat、slice、embedding/gather、reduction、linear、pad、creation防止轴、广播、收缩维和动态范围被误改
layout保持或广播、物化输出、reshape stride、transpose stride、expand 零 stride、view/物化边界防止只看 Shape 一样，却忽略存储布局语义
一个具体例子aten.mean.dim 的 keepdim=True 实际位于 kwargs。旧做法只根据输入输出 Shape 猜测，容易误判；现在审计器读取真实调用参数，再按 dim 和 keepdim 推导期望 Shape。动态 slice 的 end 如果来自运行时 SymInt，则明确记录为“元数据不足”，而不是为了提高覆盖率强行判为通过。

边界与风险：为什么现在不能说 100%

本阶段的价值在于把缺口变成可测量、可定位的工程问题，而不是用少量跑通案例覆盖所有未知范围。

已经有证据的能力

  • 三种入口汇入同一 Core ATen/PT2 产物。
  • 动态 batch / sequence 与结构化 If/Loop/Scan 有代表性 XPU 结果。
  • 语义契约随产物落盘，错误规则能够阻断导出。
  • 39 个算子族覆盖当前 22 个去重模型的语义登记。
  • 两类真实模型可执行规则比例达到 86% 以上且无失败。
  • 代码已提交并推送到 origin/dev/hx。

仍需继续完成的能力

  • 尚未取得并扫描全部 250/500 模型。
  • 符号 reshape 元素数量等价证明仍是最大元数据缺口。
  • 矩阵逻辑轴 layout、运行时 Shape 查询规则尚待实现。
  • CNN、检测、生成式模型和长序列动态范围覆盖不足。
  • PyTorch 2.5 与 2.9 的 PT2 序列化兼容尚未统一。
  • 语义覆盖、转换覆盖、Core ATen 导出和 XPU 执行需要分别统计。
禁止混用的三个概念“注册表认识这个算子” ≠ “onnx2torch 能正确转换” ≠ “FlagTree/XPU 已有稳定高性能 Kernel”。汇报时必须分别说明语义层、转换层和后端执行层的证据。

下一步建议：从单模型成功走向规模化可交付

下一阶段不建议继续只用“又跑通一个模型”衡量进展，而应建立分层漏斗：每个模型在哪一层失败、失败原因是什么、修复能覆盖多少同类模型。

补齐高频规则

优先实现符号 reshape 元素数量证明、矩阵逻辑轴 layout、运行时 Shape 查询元数据。它们覆盖当前大多数未判定项。

批量审计 250/500

直接复用现有 PT2 审计工具，形成语义、转换、导出、XPU 四张独立清单，不再把一个百分比混作全部完成度。

扩展模型类型

从 BERT 类扩展到 CNN、检测、生成式模型；补充复杂 Slice/Range、多输出 Shape 与更长 sequence 边界。

性能与版本工程

定位 20 分钟级编译慢点，建立 PT2 版本策略；CI 暂缓，但保留脚本化复验入口，后续再自动化。
